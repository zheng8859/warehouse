## Context

动机见 `proposal.md` 的 Why。这里只记影响做法的现存事实：

- `decode_session_token` 的校验顺序是**结构 → 算法 → 签名 → 载荷语义**
  （`app/core/security.py:202` 的 docstring；验签在 `:228`，解释载荷在 `:232` 起）。
  这个顺序本身就是本 change 的判断依据 —— 它决定了哪些失败原因对未认证方可见。
- 401 有**两个**产生方：中间件（在 `app.exception_handler` 之外，自己构造响应）与
  登录端点（抛 `DomainError` 走处理器）。阶段二已把两处的渲染收进
  `app/core/errors.py::error_body`，故形状是结构上统一的，不需要本 change 再动。
- `_unauthorized(str(exc))`（`app/api/middleware.py`）是当前把失败原因带出中间件的
  **唯一**通道；`app/main.py` 有 logger，但认证路径一行都不记。
- `openspec/specs/auth/spec.md` 是阶段二归档时建立的主规格，其「登录端点与失败语义」
  一条正文覆盖两件事（登录端点的免认证+失败语义、凭据校验路径的 401），
  这正是那句话被写宽的土壤。

## Goals / Non-Goals

**Goals:**

- 让 `auth` 规格与该能力的**事实来源**（`13` §6.1、`22` §2.1/§2.3）口径一致：
  登录失败「不区分」有来源 → 保留并限定在登录端点；凭据校验路径「不区分」无来源 → 撤掉。
- 把「凭据校验的 401 区分原因」**写成正向要求**，一次性了结反复被当缺陷挑出来的问题。
- 订正 `app/api/middleware.py` 类 docstring 里与代码不符的那半句。

**Non-Goals:**

- 不改任何 401 的状态码、响应体形状或文案内容；不改 `security.py` 的任何 message。
- 不引入认证路径日志（见 Open Questions）。
- 不碰 `permission` 能力、不碰 `ROLE_PERMISSIONS` 矩阵、不引入任何 `resource.action`
  相关的判定 —— 本 change 不涉及权限决策，只涉及「未通过认证时怎么回应」。
- 不涉及 cap、台账、LLM、前端，故本 change 无性能与事务语义上的影响：无新增查询、
  无写路径，也不新增任何模块间调用 —— `08` §14.1「各模块间的接口契约」那张表里
  没有认证相关的一行，故其 SLA 一栏（解析 ≤5min / cap ≤100ms / 单物料 ≤1s /
  写入 ≤200ms / 后验 ≤1s / 刷新 ≤3s）一条都不触及，本次也无需为它新增行。

## Decisions

### D1：改规格，不改代码

三个备选：

- **(a) 把中间件的 401 收敛成统一文案** —— 与规格字面一致，但要动 `test_auth.py` /
  `test_token.py` 的若干断言，且**净损失诊断力**：线上一个 401 将分不清过期、被吊销、
  还是载荷被改，而排查「管理员置 `disabled` 后旧凭据为何仍通行」正需要它。
- **(b) 代码不动、规格也不动** —— 下次评审会再挑出来一遍，且这次已经证明「读规格的人
  会以为中间件违规」。
- **(c) 加日志保留原因 + 统一文案** —— 兼顾，但改动最大，且为一条 message 开一个
  可观测性口子，方向本末倒置。

**取 (a) 的反面**：改规格。判据是**事实来源**不是偏好 —— 全 `产品设计/` 文档 grep
「不区分」零命中，`13` §6.1 第 3 步只要求「返回 HTTP 401，前端引导至登录页」；
`CLAUDE.md` 定的是「设计文档是事实来源，代码是它的派生物」，此处**规格比事实来源宽**，
该收敛的是规格。

### D2：规格里保留「区分原因」的**正向**要求，而不是删掉了事

只删「不得区分失败原因」会让规格对这件事**沉默**，下一个人仍可能把它当缺陷"修"掉 ——
本轮评审就是这样发生的。故写成正向要求并附上理由（与登录端点相反、逐因文案只在验签
通过之后可达），再配一个场景作为可测落点。这属于 `## MODIFIED` 的正当内容：改的是同一条
Requirement 的行为规定，不是新增一条 Requirement。

### D3：场景只增一个，且用**差异**断言

新增的场景断言「过期凭据与签名被篡改的凭据，两次 `message` 不相同」。刻意不写死具体文案 ——
文案属实现细节，规格钉的是「可区分」这个性质；写死文案会让任何一次措辞润色都要改规格。

### D4：docstring 订正成**有来源**的那条边界

真正的硬边界是**不返回 404、不泄露路由是否存在**（`permission` 能力的「访问边界与
免认证白名单」有明确要求，且 `test_smoke.py` 已钉住）。原句「不区分原因（避免成为探测面）」
既与代码不符，又是这句规格被写宽的源头，改为写「一律 401，不返回 404」。

## Risks / Trade-offs

- **[规格正向要求「区分原因」与「失败信息越少越安全」的直觉冲突]** → 要求文本写明与登录
  端点相反的理由，并限定「只在签名校验通过之后可达」；D3 的场景把它钉住，改动前必须
  先回答「为什么这次要区分」。
- **[逐因文案里含 claim 名与类型名]**（「会话凭据的 `exp` 类型不合法（期望 int…）」）→
  它落在验签之后，可见者要么是合法签发方、要么已持密钥，故可接受；但若日后有人把
  表名/列名/内部路径加进这些文案，就越过了「诊断信息」的边界。本 change 不改变这些文案，
  也不为其背书到那一步。
- **[唯一的代码改动是一行 docstring]** → 零回归风险；546 例测试不受影响，仍须全绿后再提交。
- **[归档后回滚成本]** → 规格一经归档同步进 `openspec/specs/auth/spec.md`，反向修改需要
  另开一个 delta change。这是 OpenSpec 既定流程，不额外缓解。

## Migration Plan

无数据迁移、无接口迁移、无需停机。合并进 `main` 即可：docstring 改动随代码生效，
规格改动在 `/opsx:archive` 同步主规格时落地。

回滚：`git revert` 本 change 的提交。若已归档，需另开一个 delta change 把规格改回去 ——
不能直接编辑主规格。

## Open Questions

- **认证路径是否补日志**（把失败原因记进日志、响应仍逐因）。它能进一步提高可诊断性，
  但要为一条 message 引入认证路径的日志设施；建议随阶段三之后的统一可观测性一起做。
  与本次规格、做法、任务拆分均无关，故不阻塞。
