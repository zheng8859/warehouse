## Context

动机见 `proposal.md` 的 Why。本节只记**本设计必须迁就的现状**，它们决定了下面多数决策的形状。

**代码侧**：`app/engine/` 的 8 个文件（`__init__` + 7 个模块）全是 docstring 骨架，每个骨架已注明事实来源章节 —— 模块切分是**既定的**，本设计只填内容，不重划边界。`app/api/routes/allocate.py` 只有一个空 `APIRouter`，模块 docstring 明确「**不预置桩端点**，端点按 TDD 先写测试再实现」。`app/core/config_version.py` 已经实现好「当前生效版本」的选取（`pick_current_version`），引擎**必须复用它**而不是自己写一遍。`app/models/configuration.py` 的 `WEIGHT_FACTORS` 元组已钉死六因子的**列的列举顺序**。

**模型侧**（决定了哪些事引擎**做不到**，这比能做什么更重要）：

| 现状 | 后果 |
|---|---|
| `WeightConfig` 六列**没有** Python 侧默认值 | 权重缺席只能阻断，不能静默取默认 |
| `CapacityConfig` 六项**有** Python 侧默认值（取自 `16` §353~356 表值） | 容量口径缺席按文档默认跑 |
| `AisleCap` 只有 `cap_total` / `cap_reserved` / `cap_usable` / `is_near_station`，**没有** `cap_used` | 事务内增量不落本表；增量的唯一来源是 `Ledger` |
| `Aisle` 只有 `total_cells` / `is_near_station`，**没有**「停用/可用」列 | 「巷道可用」判据没有列级来源 |
| `Aisle.is_near_station` 与 `AisleCap.is_near_station` 均**可空**，NULL = 「未导出」，不得当 `False` | 近站台判定必须处理「未知」 |
| `AisleStation` 首期为**空表**（`16` §1.1 / 附录 A.4 写明待业务方导出） | `station` 因子与「次近巷道」分档都没有数据 |
| `InventoryItem.zone` 列**仍在**，但其**全部文档来源已清退**（`17` §3.3 / `16` 附录 A.1~A.3 与总表 / PRD 数据来源表） | 该列已无来源、无用途；引擎**不读它**，列本身的清退见 D7 |
| `JobOrder.qty` 的单位未定（`tasks.md` 9.4c 已登记），`AisleCap` 的量是**格** | 单量 → 格 的换算规则缺位 |
| `17` §10.7（本变更新增）的 `snapshot_version` 是 `"2026-09-08T00:00"` 串，而 `Snapshot` 存的是 `version_no` 整数 | 响应里的版本串是 `snapshot_time` 的**渲染**，不是 `version_no` |

**本阶段无真实数据**：四类输入（cap 基线、既有库位分布、ABC 分类、巷道-站台主数据）全为空，这是 `16` §394 / `A.4` 写明的预期状态，不是缺陷。所以本设计的验收方式是**造数单测**：用内存库塞入最小数据集，断言评分与分配的每一步。

## Goals / Non-Goals

**Goals:**

- 把 `14` §二~§3.5 的批量分配流程落成 7 个模块的**单向调用链**，每一环都能单独用造数单测驱动
- 让「同样输入必得同样输出」成为一条**可被测试断言的性质**，而不是一句承诺：写出全序规则、定点比较规则和时钟注入点
- 把三种同名「降级」按模型已给出的形状分开承载（列 vs JSON），不新增列、不新增台账
- 数据缺失时**不阻断作业**，而是降级并在推荐理由中写明 —— 这正是首期唯一能跑通的形态

**Non-Goals:**

- 不重新论证 6 因子的集合、权重口径、算法族（贪心 vs 全局最优）—— 均为 `14` 既定决策
- 不做 cap 的持久化增量、漂移对账与告警（属 F9 / 阶段四）：本阶段**只读** `AisleCap` 基线，扣减发生在内存
- 不为「次近巷道 / 远巷道 / 溢出区」编造分档阈值（理由见 D5）—— 缺的是数据源，不是常量
- 不做导入管线、落位执行、后验、KPI；不写任何 `Ledger` 行
- 不引入任何新依赖、新表、新列；不碰前端

## Decisions

### D1 模块切分与单向调用链

7 个模块的依赖方向**只有一条**（骨架 docstring 已按此写就）：

```
priority.py    ──┐                        （队列序，不参与选道）
                 ├─→ allocator.py ─→ reasons.py
factors.py ─→ scoring.py ─┘      ↑            ↑
                          reserved.py    degradation.py
```

- `factors.py`：六个**纯函数**，输入是「一个巷道 + 本单 + 只读快照」，输出 `[0,1]` 的值与一句取值说明。不碰 DB（由调用方取好数据递入）。
- `scoring.py`：解**可行巷道集**并对其中每个巷道求综合分。
- `priority.py`：只算队列序，输入不含任何因子分。
- `allocator.py`：主循环（排序 → 逐单取可行集 → 选最高分 → 扣减 → 下一条 → 回溯预测跨巷道）。它**向下**调 `reserved` / `degradation` / `scoring` / `reasons`。
- `reserved.py`：预留池的可用量函数与超时释放判定。
- `degradation.py`：分档（D5）与降级原因措辞。
- `reasons.py`：按 `17` §10.1 组装 `payload_json`（含 `17` §10.7 的响应侧字段）。

**为什么按这个方向**：`14` §一 的第二条原则是「资源仲裁与位置选择分离」。依赖方向是这条原则的结构化表达 —— `priority` 不 import `scoring`、`scoring` 不 import `priority`，**两者无法互相影响，除非有人改 import**。备选：全塞进 `allocator.py` 一个文件。被否 —— 那样「两件事分离」就只是注释里的一句话，而注释不会在有人图方便时拦住他。

### D2 确定性的落法：全序、定点比较、时钟注入

红线「同样输入必得同样输出」在实现层要落成四件具体的事，缺一件就会漏出不确定性：

1. **一切遍历序必须显式给出，不得依赖 DB 返回序或集合迭代序。** 候选巷道一律按 `aisle_no` 文本升序；队列一律按 `(priority 降序, job_order_id 升序)`；因子求和一律按 `WEIGHT_FACTORS` 元组的顺序。`set` 只用于去重（如预测跨巷道的巷道并集），**取用时必须 `sorted()`** —— Python 的 `set` 迭代序对字符串受 `PYTHONHASHSEED` 影响，同一份数据在不同进程里可能给出不同顺序，这是最隐蔽的一类不确定。
2. **得分比较在量化后做，不用浮点 `==`。** 总分按 `17` §10.1 的口径 `Decimal(str(x)).quantize(Decimal("0.01"), ROUND_HALF_UP)` 取两位小数，**比较量化后的值**；浮点原值只参与计算不参与判等。理由不是洁癖：`0.575` 这类恰好落在半值上的数在二进制浮点下 `round()` 会给 `0.57`，用它排序会让「看起来相等的两个巷道」在两次运行里排出不同名次。
3. **`now` 是显式入参，引擎内部不调 `datetime.now()`。** 超时释放判定依赖当前时刻（D5 / `reserved.py`），若引擎自己取时钟，「同样输入」就不再是同样的输入。路由层取一次 `now` 并向下传，测试传固定值。这样「同一队列 + 同一快照 + 同一 `now` ⇒ 同一输出」是一句可断言的话。
4. **不引入任何随机源**：无 `random`、无 `uuid4`、无外部调用。批量批次号看似需要唯一性，也按 D11 的确定性规则生成。

**备选**：把「确定性」交给测试的两次调用比对。被否 —— 两次调用若都在同一进程内，`PYTHONHASHSEED` 与字典序恰好相同，测试会**通过**而线上跨进程仍可能不一致。要靠结构（全序）而非靠观察。

### D3 配置取数：权重阻断、容量按文档默认

| 配置 | 缺席时的行为 | 依据 |
|---|---|---|
| `WeightConfig` | **阻断**本次评分，提示配置未就绪，不产出方案 | 六列无 Python 默认值；spec `recommendation-engine`「评分权重的来源与缺失处置」 |
| `CapacityConfig` | 用文档默认值（40% / 18:00 / N=5 / 5 / 3 / 1%）跑 | 六项均有列默认值，且 `configuration.py` 明写「配置缺席时按文档默认跑，而不是随代码猜一个数」 |

取当前生效版本**复用** `app/core/config_version.py` 的 `pick_current_version`（判据 = `effective_at <= now` 中 `version_no` 最大者）。**不自己写一遍取版本的查询** —— 那段的口径（为什么是 `version_no` 最大而不是 `effective_at` 最新、为什么不用指针列）已经在那个模块的 docstring 里论证过，重写等于制造第二个口径。

**这个不对称不是我定的，是模型层已经做出的区分**：`WeightConfig` 六列没有默认值，`CapacityConfig` 六项有。引擎只是兑现它。理由也成立：权重是**打分口径**，缺席时取默认会产出一个「看起来正常、但没人批准过」的排序，且它直接决定谁先挑黄金库位；容量六项是**物理约束的保守默认**，`16` §353~356 给了表值，缺席时按表值跑与文档一致。

### D4 容量扣减不落库 —— 本阶段没有台账，就没有增量

**决策**：一次批量分配内，容量扣减只发生在**进程内的快照副本**上，不写 `AisleCap`、不写 `Snapshot`、不写 `Ledger`。第二次调用重新从 `AisleCap` 基线读起，因此**同样的入参两次调用得到完全相同的输出**。

**为什么**（三条，缺一条都不足以定案）：

1. `linkage.py` 的 `AisleCap` docstring 已钉死：「事务内增量**不落本表**：它靠 `Ledger` 同事务更新，**台账是 cap 增量的唯一来源**（`16` §6.3）」。本阶段不写台账（落位执行属 F7 / 阶段四），所以增量无处可落。
2. 落库会造出与 `Ledger` **平行的第二套 cap 增量来源**，直接撞两条红线：「台账只有一套，不新增平行台账」与「cap 与台账同事务写入必须由真实事务保证」。
3. **语义上也不该落**：分配产出的是**方案**，方案未经操作员逐单确认（L1）。把未确认的方案算进库容，等于让「未确认」产生了持久影响 —— 与「未确认不产生台账」是同一条红线的两个面。

**备选 (a)**：写一个内存外的 `cap_used` 表。被否 —— 见第 1、2 条，且 `AisleCap` 刻意没有 `cap_used` 列。
**备选 (b)**：落库但在事务末尾回滚。被否 —— 徒增写放大（SQLite 单写库），而结果与不写完全一样。

### D5 四级降级链的分档：由数据源的可表达性决定，不编造阈值

`14` §3.5 / `15` §4.4 给了链的**名字**（近站台 → 次近巷道 → 远巷道 → 溢出区），但**没有给分档阈值**，也没有定义「溢出区」的物理形态。而现有数据只能表达两档：

| 档位 | 本阶段的成员判据 | 数据源 |
|---|---|---|
| 0 近站台 | `AisleCap.is_near_station IS TRUE` | 布尔列，有 |
| 1 次近巷道 | **空集** | 需要 `AisleStation.distance_weight` 的**分档阈值**，文档未给；且该表首期为空 |
| 2 远巷道 | `AisleCap.is_near_station IS FALSE` | 同档 0 |
| 3 溢出区 | **空集** | 文档称其为最后一档，但未定义它是不是 `aisles` 之外的一块区域 |

**决策**：`degradation.py` 暴露一个**档位解析器**，返回「有序的巷道分组列表」，分配器对它有 4 个位置**逐档下探**、记录首次可行的档位并写入降级原因。本阶段的解析器只填档 0 与档 2；档 1 与档 3 为空集，下探逻辑照常经过它们（空集 ⇒ 直接进下一档）。

**为什么留空而不是给个默认阈值**：分档阈值是**业务口径**（多近算「次近」？），不是工程常数。填一个数会让「为什么这单算次近」在操作员追问时答不上来，而且阈值一旦随数据分布浮动，同一天的两次分配可能给出不同档位 —— **编造一个阈值比留一个空档更糟**。档位语义与阈值一并列入待业务方确认（D14）。

**溢出区走尽之后**：`15` §11.1 写着「溢出区仍不可行 → 该单标记失败并提示人工介入，**不静默落位**」。所以四级走尽**不等于**降级成功 —— 该单产出「分配失败」的结果、**停留在 `PENDING`**（`15` §3.1 的 `PENDING → PENDING：批量分配失败可重试`），并提示人工介入。它不进入 `PLANNED`，也不写 `bulk_batch_no`。

### D6 「板-格」换算收在一个函数里，首期取恒等

`JobOrder.qty` 的单位未定（`tasks.md` 9.4c 登记在案），`AisleCap` 的量是**格**，`Material.cartons_per_pallet` 的单位文档也没说（`17` §2.3 只说「按单厂换算规则内置」）。而「cap 是否足够」这个判据两边都要用。

**决策**：`allocator.py` 只通过**一个**函数 `to_occupied_cells(qty, material)` 得到占用格数；本阶段该函数返回 `qty`（即**一单一位 = 一格 = 一板**的恒等），并把换算规则登记为待确认（D14）。

**为什么恒等是唯一站得住的首期读法**：`14` §2.2 的算例自己就用板做巷道容量的单位（「近站台巷道（01/02）合计剩 **100 板**」），`14` §3.5 的告警文案也是板（「近站台缺口 X **板**」），`08` §14.1 与 `CLAUDE.md` §十 的验收指标同样是板。也就是说**文档自己的算例把「板」与「格」当同一个量在用**。恒等是唯一与全部文档算例自洽、且不需要发明任何换算系数的读法；把换算隔在一个函数里，是为了规则到齐后只改一处、不动分配器。

### D7 可行巷道集的三个判据，各自的取数源

`14` §3.4 步 1 给了**三个**判据（原为四个，第四个「品质库区匹配」已按用户决定从全部文档移除，调查与处置见下）。逐个落到本阶段的取数源上：

| 判据（`14` §3.4） | 本阶段实现 | 说明 |
|---|---|---|
| `cap 足够` | `available_cap(...) >= to_occupied_cells(...)` | 见下方公式 |
| `巷道可用` | `Aisle` 主数据存在该 `aisle_no`，且该快照有对应的 `AisleCap` 行 | 见下方 |
| 非 A 类排除预留池 | 见 `available_cap` 的 ABC 分支 | — |

```
available_cap(cap: AisleCap, abc_class, now) -> int:
    if abc_class == A:               return cap.cap_total      # A 类可用含预留的总额
    if now.wall_clock >= release_at: return cap.cap_total      # 超时释放后 B/C 同享
    return cap.cap_usable                                      # 非 A 类仅可用部分
```

- **释放判定用现场墙上时间**，与 `CapacityConfig.reserved_release_at`（`Time`，当日钟点）同一时钟口径。`configuration.py` 已就此写明：按 naive UTC 比会让现场变成**次日 02:00** 释放。`now` 由路由注入（D2 第 3 条）。
- **「巷道可用」的取数源是主数据存在性，不是状态列。** `Aisle` **没有**「停用」列。备选是给 `Aisle` 加一列 —— **被否**：`17` §2.1 的字段表没有它，而 data-model 阶段已确立「**不替文档补列**」的原则（`CapacityConfig` 特意不加 `changed_by_id`、`ConversationContext` 特意不加 `updated_at`，都是同一条原则）。「停用巷道」在本阶段是一个**尚不存在的概念**，用主数据存在性表达它，含义准确且零改动。
- **`is_near_station IS NULL`（未导出）不需要特判**：预留池只在近站台非零，未导出时快照侧的 `cap_reserved` 本身就是 0，于是 `cap_usable == cap_total`，`available_cap` 自然收敛到「所有人可用全额」。**以快照三列为准**（快照是权威）；若出现「`is_near_station` 为空而 `cap_reserved > 0`」这种自相矛盾的行，仍以 `cap_*` 三列为准，并在因子级降级标记中记明。

**第四个判据「品质库区匹配」已移除（本变更的调查与处置）**：`14` §3.4 步 1 原列四个判据，第四个是这四个字，而它**全文只出现一次，且从未被定义**。文档里有两个容易被读成它的字段，但**都不是它**：

| 字段 | 是什么 | 文档写的用途 |
|---|---|---|
| `InventoryItem.item_status` | 品质状态：`合格` / `待检` / `冻结…`（`17` §3.3 的字段枚举） | 「**判定是否计入可用库存**」（`16` 附录 A.1 #8），INV 模版**必填** |
| `zone`（库区号） | 分区号，示例 `A` | 「**分区统计**」（`16` 附录 A.2 / A.3 原第 5 行），选填 |

两种可能读法**都缺前提**，且缺在不同的地方：

1. **读法一（`zone` 匹配）** 需要「巷道/库位 → 库区」映射。**模型里不存在**：`Aisle` 无 zone 列，`Location` 有 `status` 也无 zone 列。更硬的一处：`zone` 只落在库存行与单据行上，而 `17` §4.1 的 `JobOrder` **连 `zone` 列都没有** ⇒ `16` 附录 A.2 / A.3 里「库区号 → `zone`」那两行映射**从来没有落点**。
2. **读法二（品质状态 ↔ 库区，如「待检品进待检区」）** 需要一张「库区 → 允许哪些品质状态」的规则表，**文档里没有**。且它的实质是**按品质状态分派库区**，撞 `16` 附录 A.1 #8 与 `CLAUDE.md` §九 的边界：「**待检状态转换 / 品管联动不归本系统**」（属品管流程，独立主线另做）。

### D8 三种「降级」分开承载，一个字都不共用

「降级」在本项目有**四个**同名概念，本阶段涉及前三个（第四个属阶段四的导入回执）：

| 概念 | 含义 | 承载字段 | 出现在 |
|---|---|---|---|
| **方案级** | 容量不足，走了降级链 | `RecommendationPlan.degraded` / `degrade_reason`（**列**，带 DB CHECK） | 理由卡标题区 |
| **因子级** | 某因子数据缺失，该因子不参与评分 | `payload_json.factor_degraded`（**JSON 键**，无列） | 理由卡的因子行 |
| **排序降级** | 缺未来 N 天出库量，队列退化为仅按 ABC 排序 | `payload_json.priority.degraded` / `degrade_reason` | 队列项 |
| 导入降级链 | 导入侧的分流处置 | `ImportSession` 回执（阶段四） | 导入页 |

**决策**：列级**只承载方案级**，因子级与排序降级进 `payload_json`。这不是权宜 —— 它正好是模型已经给出的形状：`RecommendationPlan` 有 `degraded` / `degrade_reason` 两列且带 `CHECK(degrade_reason_required)`（「降级不静默」落成库层约束），而**没有** `factor_degraded` 列。给因子级补一列会让「这个方案的 `degraded=True` 到底指容量不足还是数据缺失」重新变得不可判 —— 正是 spec 里「两种降级不得混用」要拦的那件事。

### D9 推荐理由的组装边界

`reasons.py` 按 `17` §10.1 组装 `payload_json`，并保证三条不变量（都有对应测试）：

1. **每个参与评分的因子都有取值与取值说明**；降级因子**不出现**在分解里（否则操作员会看到一个值为空的因子，误以为它参与了打分）。
2. **`scores[巷道]` 恒等于「可用因子加权和 ÷ 可用因子权重之和」**（两位小数）。`17` §10.1 已论证：权重和不等于 1 时这个归一化是纯比例缩放，不改变同一次运行内的相对次序。
3. **列与 JSON 不打架**：`RecommendationPlan.degraded` / `degrade_reason` 与 `payload_json` 里的同名字段是**同一次写入的投影**，必须一致（`RecommendationPlan` 的 docstring 已把这层关系写明）。因子级降级**只在 JSON 里**，不投影成列。

「预测跨巷道」由分配器在**全部队列处理完后回溯**计算（`14` §3.4 步 5）：`| 既有快照中该物料占用的巷道 ∪ 本次分配给该物料的巷道 |`，阈值取 `CapacityConfig.same_material_cross_aisle_threshold`（默认 5）。既有占用的取数 = 当前快照的 `InventoryItem` 中该 `material_code` 的行按 `substr(location_code, 1, 2)` 去重 —— 切片而非数值化，`CLAUDE.md` §七。**同批跨巷道不预测**（PO 不含批号，分配时刻无批号可聚合）。

### D10 端点契约与权限口径

`POST /api/allocate/batch`，请求体 `{warehouse_id, snapshot_version?, job_order_ids[]}`（`17` §10.7）。

- **`job_order_ids` 必填、无隐含默认**。不设「空即全量」：那会让同一份数据按调用方的不同意图产出不同结果，直接撞「同样输入必得同样输出」。空数组 = 明确的空集，产出空 `plans`。
- **单次上限 50 单**，超出拒绝并提示拆分，**不静默截断**（静默截断会让调用方以为 51 单都分配了）。
- 只处理 `PENDING`，其余状态**整体拒绝**（不部分成功）。不新增 `PLANNED → PLANNED` 等未定义迁移。成功者写 `bulk_batch_no` 并迁 `PLANNED`。
- 响应 `plans` 按 `priority` 降序；`plan_id` 指向 `RecommendationPlan`，**理由体按 `plan_id` 另取**，不在响应里复制一份（避免同一份理由有两个可能分叉的副本）。
- `snapshot_version` 出参是 `Snapshot.snapshot_time` 的 `"%Y-%m-%dT%H:%M"` **渲染**（`17` §10.7 的展示形状）。**不要把 `Snapshot.version_no` 塞进它** —— `Snapshot` 的 docstring 已写明存储层用 `id` 作被引用键、时间戳串只作展示。

**权限**（design rule：写明 `resource.action` 并对照 `13` 的矩阵）：

- 资源标识 = **`inbound.operate`**（该端点由入库作业的批量分配动作触发）。
- `app/api/permissions.py` 的 `ROLE_PERMISSIONS` 对照：`warehouse_keeper` ✅、`admin` ✅（`AUTO_ONLY` 之外的全集）；`planner` ❌、`supervisor` ❌（矩阵里主管**没有** `inbound.view`，注释明写「入库执行不归主管」）。
- **`engine.invoke` ∈ `AUTO_ONLY`（`permissions.py:75`），恒不授予任何角色**，且 `check()` 里这条判断**先于**查表。故「引擎调用本身不向任何角色暴露」是**代码已保证的事实**，不是本阶段新增的约束。文档 `27` 的「仅授权角色」表述与此冲突，以 `13` + `CLAUDE.md` 为准（已订正，见 D13）。
- **本阶段不挂 403**：`permission` 规格的「v1 不做端点级资源鉴权」仍然有效，越权由角色菜单可见性 + 二次确认承担。本端点的 **401 由既有认证中间件覆盖**，引擎侧零新增鉴权代码。
- **已订正 `permission` 主规格的表述**（2026-09-11，按用户决定）。原条「自动写权限封闭」的正文写「任何角色都不得通过手动入口触发台账写入或引擎调用」，其场景更直言「不存在面向角色的手动触发端点」—— 本端点恰恰是持 `inbound.operate` 的角色**可调**、且**会触发引擎**的，字面上正面冲突。

  订正**不改实质**（`engine.invoke` 恒不授予这条，`AUTO_ONLY` + `check()` 先于查表已保证），只把口径从**端点级绝对**收回**资源级**：不得以 `ledger` / `engine` 为**目标资源**设手动接口，而引擎调用作为**业务动作的内部后果**发生、授权依据是该业务动作的资源标识。依据是 `13` §2.2 的 `engine` 行原文「`invoke`（系统内部调用，**不向业务角色开放手动触发**）」与同节图例「自动 = 由作业流 / 引擎自动执行，不向角色暴露手动入口」—— 两条讲的都是**资源不得被授予**，不是「系统不存在任何会触发引擎的端点」。

  落地在 `specs/permission/spec.md` 的 `MODIFIED Requirements`：携带整条需求（正文订正 + 两条原场景保留，其中「引擎调用无手动入口」的 THEN 收紧为「不存在以 `engine` 为**目标资源**的端点」）+ **一条新场景**「业务动作间接触发引擎不算手动入口」固化这个读法。**主规格要到归档时由 delta 同步** —— 在此之前 `openspec/specs/permission/spec.md` 仍是旧措辞，这是 OpenSpec 的正常时序，不是遗漏（见 Risks）。

### D11 批量批次号的生成规则

`BAT-<现场日期 YYYYMMDD>-<当日序数 NN>`（形状取自 `17` §10.7 的示例 `BAT-20260908-01`）。`NN` = 当日已有批次号的数量 + 1，在同一事务内由 `JobOrder.bulk_batch_no` 的日期前缀计数得出。

- **日期用现场日期**，不是 naive UTC —— 沿用 `CapacityConfig.reserved_release_at` 已经立下的口径：给现场看的「当日」= 现场墙上时间的那一天（`18:00` 指现场的 18:00）。
- 规则必须**确定**（D2）：不能用 `uuid4`、不能用随机后缀。同一份入参两次调用应得到同一个批次号 —— 第二次会因为前一次的 `JobOrder.bulk_batch_no` 已回写而得到 `NN+1`，这是**入参已变**（作业单状态不再是 `PENDING`，第二次会被拒），不是不确定。
- `bulk_batch_no` **不是唯一键**（模型没有给它唯一约束）—— 它是追溯用的分组标签，不是业务主键，故不为它加约束。

### D12 失败与恢复路径

| 失败 | 影响面 | 恢复 |
|---|---|---|
| 权重配置不存在 | 整批 | **阻断**，不产出方案；配好权重后重试（`WeightConfig` 无默认，D3） |
| 队列含非 `PENDING` 单 | 整批拒绝 | 调用方剔除后重试；**不做部分成功** |
| 队列超 50 单 | 整批拒绝 | 拆分后分批调用 |
| 四级降级链走尽 | 单条 | 该单**停留 `PENDING`**、提示人工介入（`15` §11.1）；同批其余单照常出方案 |
| 写库异常 | 整批 | 一个事务内完成全部写入，异常即**整体回滚** —— 不留「一半单有方案、一半没有」的中间态 |
| 需要回滚整个功能 | 全局 | 一键关闭推荐、恢复均分。**本阶段无开关**（`14` §2.1 未要求），开关属阶段六的 Go/No-Go 闸门；届时为**功能开关式**，**不删历史台账** —— 本阶段不产生台账，故此项在本阶段无实际落点，仅登记接口预留 |

「未确认不产生台账」由**不写台账**直接满足（本阶段没有任何写 `Ledger` 的代码路径）。

### D13 关键路径与阶段表的排序不一致（记录）

`CLAUDE.md` §六 与 `openspec/config.yaml` 的关键路径是 `F1 → F2 → **F9** → **F3** → F4 → …`，而阶段表把 F3/F4 放在**阶段三**、F9（cap 自维护）放在**阶段四**。两者不自洽。

`发动机 · 27` 的「仅授权角色」表述与 `13` / `CLAUDE.md` 冲突，已按 D10 订正为「`engine.invoke` 恒不可授予，端点资源标识为 `inbound.operate`」—— 以 `13` + `CLAUDE.md` 为准（本会话已确认）。

## Risks / Trade-offs

- [**首期无真实数据，评分质量无法验证**] → 这不是风险而是既定安排（`16` §394）；本阶段验收的是**算法本体的正确性与可追溯性**（造数断言 + 理由可复算），数据侧的验收在阶段四/六。明确不声称「推荐质量已达标」。
- [**「次近/远/溢出区」留空 ⇒ 降级链实际只有两档**，与 `14` §3.5 的字面四档不符] → 链的**结构**是四档且逐档下探（空档直接跳过），字面差异只在档位成员上；D5 已论证「编造阈值比留空更糟」。**如实报告**，不声称四级已全通。
- [**恒等换算使 cap 判断在真实数据下会偏**] → 隔离在 `to_occupied_cells()` 一个函数体；规则到齐前，所有 cap 数值都是**同一口径下的相对比较**（本次批量内部的竞争关系正确，绝对可行性待定）。已在 D14 登记。
- [**内存扣减 + 不落库 ⇒ 两次并发调用会各自看到全额容量**] → 单进程单写（`CLAUDE.md` §四），且本阶段分配不产生持久影响（未确认不落库）。真正的容量竞争一致性属 F7 落位执行（阶段四，与台账同事务 + 乐观锁）。
- [**`Decimal(str(x))` 量化在极小数上有可观误差**] → 只用于**展示与比较**两位小数，不用于累加；累加走浮点、比较走量化后值（D2 第 2 条）。测试期望值**必须避开恰好落在半值上的数**（`17` §10.1 已就此写明）。
- [**`snapshot_version` 被误接到 `Snapshot.version_no`**] → D10 已写明它是 `snapshot_time` 的渲染；`Snapshot` 的 docstring 亦已写明存储层用 `id` 作引用键。`17` §10.7 的示例串与 `version_no` 整数**形态不同**，接错会立刻在测试里显形。
- [`14` §3.4 步 1 曾把「品质库区匹配」列为活判据，而这四个字文档从未定义] → **已按用户决定从全部文档移除**（`14` / `16` 总表与 A.2·A.3 / `17` §3.3 / PRD 两行 / `CONTEXT.md`），逐处改动面见 D7。残留一项：`InventoryItem.zone` **列**的文档来源已全部清退，列本身待独立清退（不由本变更夹带，见 D7）。
- [`permission` 规格的「不存在面向角色的手动触发端点」与本端点并存，字面上有张力] → **已了结**：用户 2026-09-11 决定「订正」，已落 `specs/permission/spec.md` 的 MODIFIED delta（**实质未变** —— 只把口径从端点级绝对收回资源级，与 `13` §2.2 对齐；详见 D10）。**遗留一项时序**：主规格 `openspec/specs/permission/spec.md` 要到归档同步时才换措辞，在那之前它仍是旧的 —— 故本变更归档前，**不得以「主规格已经对了」为前提**去判断任何与 `engine` / `ledger` 手动入口有关的行为。
- [**未导入任何映射 ⇒ 端点在没有种子数据时也应当行为确定**] → 空队列产出空 `plans`；无权重阻断；无 `AisleCap` ⇒ 无可行巷道 ⇒ 每单走「四级走尽 → 失败」。三条路径都有单测。

**性能目标**（引用 `08` §14.1「各模块间的接口契约」的 SLA 数值）：

| 契约（`08` §14.1） | SLA | 在本阶段的落点 |
|---|---|---|
| F3(评分) → F4(推荐)：单物料评分 | **≤ 1s** | `scoring.py` 的单物料路径；候选巷道数受主数据规模限定，全程无 IO、无外部调用 |
| F9(cap) → F3(评分)：cap 查询 | **≤ 100ms** | `AisleCap` 读路径，靠既有的 `(warehouse_id, snapshot_id, aisle_no)` 唯一约束前缀，**不另建重复索引**（该决策已写在 `AisleCap` 的模型注释里） |

`08` §14.1 **没有**为批量端点定义 SLA（那张表是模块间契约，粒度是单物料）。故本阶段自设工程上界：**50 单 ≤ 5s**（与单物料 ≤1s 同量级，且 50 是 `08` / `CLAUDE.md` 已定的单次上限）。超限视为实现缺陷，进 `tests/logic/` 的性能用例。

**确定性**：本阶段新增的全部计算（6 因子打分、优先级排序、可行集求解、贪心分配、降级链下探、理由组装）都是**纯函数 + 全序排序**，不含随机搜索、不含外部模型、不依赖字典/集合迭代序。唯一的随机源风险（批量批次号）按 D11 的确定性规则生成。`now` 显式注入（D2 第 3 条），故「同一队列 + 同一快照 + 同一 `now`」⇒ 逐项相同的输出，含 `aisles` / `scores` / `breakdown` / `priority` / 降级标记。**核心链路零外部依赖**：本阶段不 import `app/llm/`，也不新增任何第三方包。

**cap 的两条路径在本阶段的落点**：

| 路径 | `16` 的口径 | 本阶段 |
|---|---|---|

## Migration Plan

- **无数据迁移**：本变更不新增表、不新增列、不改列类型，迁移链无需 `alembic revision`。空库 `upgrade head` 后 `autogenerate` 应产生**空 diff** —— 这一条作为验收动作保留（`data-model` 变更立下的同一动作）。
- **发布顺序**：先写测试（RED，`tests/logic/test_*.py` 造数）→ 实现 7 个模块（GREEN）→ 接端点（`tests/api/`）→ 逐组件原子提交。单测不允许「先实现后补测试」。
- **回滚策略**：代码回滚 = 分支不合并，或 revert 到 `v0.2.0`；本阶段不写台账、不改既有数据，故**回滚无数据后果**。「功能开关式回滚、不删历史台账」是阶段六 Go/No-Go 的闸门要求，届时实现（D12 已登记接口预留）。
- **与阶段四的接口**：`AisleCap` 的行由阶段四写入、`RecommendationPlan` 的消费方（F5 确认 / F7 落位）也在阶段四。本阶段把契约（`17` §10.1 / §10.7）先定下来，阶段四只接不用改 —— 这正是「**27 必须先于 28**」的含义。

## Open Questions
