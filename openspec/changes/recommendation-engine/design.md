## Context

动机见 `proposal.md` 的 Why。本节只记**本设计必须迁就的现状**，它们决定了下面多数决策的形状。

**代码侧**：`app/engine/` 的 8 个文件（`__init__` + 7 个模块）全是 docstring 骨架，每个骨架已注明事实来源章节 —— 模块切分是**既定的**，本设计只填内容，不重划边界。`app/api/routes/allocate.py` 只有一个空 `APIRouter`，模块 docstring 明确「**不预置桩端点**，端点按 TDD 先写测试再实现」。`app/core/config_version.py` 已经实现好「当前生效版本」的选取（`pick_current_version`），引擎**必须复用它**而不是自己写一遍。`app/models/configuration.py` 的 `WEIGHT_FACTORS` 元组已钉死六因子的**列的列举顺序**。

**模型侧**（决定了哪些事引擎**做不到**，这比能做什么更重要）：

| 现状 | 后果 |
|---|---|
| `WeightConfig` 六列**没有** Python 侧默认值 | 权重缺席只能阻断，不能静默取默认 |
| `CapacityConfig` 六项**有** Python 侧默认值（取自 `16` §353~356 表值） | 容量口径缺席按文档默认跑 |
| `AisleCap` 只有 `cap_total` / `cap_reserved` / `cap_usable` / `is_near_station`，**没有** `cap_used` | 事务内增量不落本表；增量的唯一来源是 `Ledger` |
| `Aisle` 只有 `total_cells` / `is_near_station`，**没有**「停用/可用」列 | 「巷道可用」判据没有列级来源 |
| `Aisle.is_near_station` 与 `AisleCap.is_near_station` 均**可空**，NULL = 「未导出」，不得当 `False` | 近站台判定必须处理「未知」 |
| `AisleStation` 首期为**空表**（`16` §1.1 / 附录 A.4 写明待业务方导出） | `station` 因子与「次近巷道」分档都没有数据 |
| `InventoryItem.zone` 列**仍在**，但其**全部文档来源已清退**（`17` §3.3 / `16` 附录 A.1~A.3 与总表 / PRD 数据来源表） | 该列已无来源、无用途；引擎**不读它**，列本身的清退见 D7 |
| `JobOrder.qty` 的单位未定（`tasks.md` 9.4c 已登记），`AisleCap` 的量是**格** | 单量 → 格 的换算规则缺位 |
| `17` §10.7（本变更新增）的 `snapshot_version` 是 `"2026-09-08T00:00"` 串，而 `Snapshot` 存的是 `version_no` 整数 | 响应里的版本串是 `snapshot_time` 的**渲染**，不是 `version_no` |

**本阶段无真实数据**：四类输入（cap 基线、既有库位分布、ABC 分类、巷道-站台主数据）全为空，这是 `16` §394 / `A.4` 写明的预期状态，不是缺陷。所以本设计的验收方式是**造数单测**：用内存库塞入最小数据集，断言评分与分配的每一步。

## Goals / Non-Goals

**Goals:**

- 把 `14` §二~§3.5 的批量分配流程落成 7 个模块的**单向调用链**，每一环都能单独用造数单测驱动
- 让「同样输入必得同样输出」成为一条**可被测试断言的性质**，而不是一句承诺：写出全序规则、定点比较规则和时钟注入点
- 把三种同名「降级」按模型已给出的形状分开承载（列 vs JSON），不新增列、不新增台账
- 数据缺失时**不阻断作业**，而是降级并在推荐理由中写明 —— 这正是首期唯一能跑通的形态

**Non-Goals:**

- 不重新论证 6 因子的集合、权重口径、算法族（贪心 vs 全局最优）—— 均为 `14` 既定决策
- 不做 cap 的持久化增量、漂移对账与告警（属 F9 / 阶段四）：本阶段**只读** `AisleCap` 基线，扣减发生在内存
- 不为「次近巷道 / 远巷道 / 溢出区」编造分档阈值（理由见 D5）—— 缺的是数据源，不是常量
- 不做导入管线、落位执行、后验、KPI；不写任何 `Ledger` 行
- 不引入任何新依赖、新表、新列；不碰前端

## Decisions

### D1 模块切分与单向调用链

7 个模块的依赖方向**只有一条**（骨架 docstring 已按此写就）：

```
priority.py    ──┐                        （队列序，不参与选道）
                 ├─→ allocator.py ─→ reasons.py
factors.py ─→ scoring.py ─┘      ↑            ↑
                          reserved.py    degradation.py
```

- `factors.py`：六个**纯函数**，输入是「一个巷道 + 本单 + 只读快照」，输出 `[0,1]` 的值与一句取值说明。不碰 DB（由调用方取好数据递入）。
- `scoring.py`：解**可行巷道集**并对其中每个巷道求综合分。
- `priority.py`：只算队列序，输入不含任何因子分。
- `allocator.py`：主循环（排序 → 逐单取可行集 → 选最高分 → 扣减 → 下一条 → 回溯预测跨巷道）。它**向下**调 `reserved` / `degradation` / `scoring` / `reasons`。
- `reserved.py`：预留池的可用量函数与超时释放判定。
- `degradation.py`：分档（D5）与降级原因措辞。
- `reasons.py`：按 `17` §10.1 组装 `payload_json`（含 `17` §10.7 的响应侧字段）。

**为什么按这个方向**：`14` §一 的第二条原则是「资源仲裁与位置选择分离」。依赖方向是这条原则的结构化表达 —— `priority` 不 import `scoring`、`scoring` 不 import `priority`，**两者无法互相影响，除非有人改 import**。备选：全塞进 `allocator.py` 一个文件。被否 —— 那样「两件事分离」就只是注释里的一句话，而注释不会在有人图方便时拦住他。

### D2 确定性的落法：全序、定点比较、时钟注入

红线「同样输入必得同样输出」在实现层要落成四件具体的事，缺一件就会漏出不确定性：

1. **一切遍历序必须显式给出，不得依赖 DB 返回序或集合迭代序。** 候选巷道一律按 `aisle_no` 文本升序；队列一律按 `(priority 降序, job_order_id 升序)`（**4.3 落地**：单号同按**文本**升序 —— 它是文本字段，解析成数字会在非数字单号上抛错或静默给出另一种序；`priority` 不做两位量化，见 D18，故比较的是加权和的浮点值）；因子求和一律按 `WEIGHT_FACTORS` 元组的顺序。`set` 只用于去重（如预测跨巷道的巷道并集），**取用时必须 `sorted()`** —— Python 的 `set` 迭代序对字符串受 `PYTHONHASHSEED` 影响，同一份数据在不同进程里可能给出不同顺序，这是最隐蔽的一类不确定。
2. **得分比较在量化后做，不用浮点 `==`。** 总分按 `17` §10.1 的口径 `Decimal(str(x)).quantize(Decimal("0.01"), ROUND_HALF_UP)` 取两位小数，**比较量化后的值**；浮点原值只参与计算不参与判等。理由不是洁癖：`0.575` 这类恰好落在半值上的数在二进制浮点下 `round()` 会给 `0.57`，用它排序会让「看起来相等的两个巷道」在两次运行里排出不同名次。
3. **`now` 是显式入参，引擎内部不调 `datetime.now()`。** 超时释放判定依赖当前时刻（D5 / `reserved.py`），若引擎自己取时钟，「同样输入」就不再是同样的输入。路由层取一次 `now` 并向下传，测试传固定值。这样「同一队列 + 同一快照 + 同一 `now` ⇒ 同一输出」是一句可断言的话。
4. **不引入任何随机源**：无 `random`、无 `uuid4`、无外部调用。批量批次号看似需要唯一性，也按 D11 的确定性规则生成。

**备选**：把「确定性」交给测试的两次调用比对。被否 —— 两次调用若都在同一进程内，`PYTHONHASHSEED` 与字典序恰好相同，测试会**通过**而线上跨进程仍可能不一致。要靠结构（全序）而非靠观察。

### D3 配置取数：权重阻断、容量按文档默认

| 配置 | 缺席时的行为 | 依据 |
|---|---|---|
| `WeightConfig` | **阻断**本次评分，提示配置未就绪，不产出方案 | 六列无 Python 默认值；spec `recommendation-engine`「评分权重的来源与缺失处置」 |
| `CapacityConfig` | 用文档默认值（40% / 18:00 / N=5 / 5 / 3 / 1%）跑 | 六项均有列默认值，且 `configuration.py` 明写「配置缺席时按文档默认跑，而不是随代码猜一个数」 |

取当前生效版本**复用** `app/core/config_version.py` 的 `pick_current_version`（判据 = `effective_at <= now` 中 `version_no` 最大者）。**不自己写一遍取版本的查询** —— 那段的口径（为什么是 `version_no` 最大而不是 `effective_at` 最新、为什么不用指针列）已经在那个模块的 docstring 里论证过，重写等于制造第二个口径。

**这个不对称不是我定的，是模型层已经做出的区分**：`WeightConfig` 六列没有默认值，`CapacityConfig` 六项有。引擎只是兑现它。理由也成立：权重是**打分口径**，缺席时取默认会产出一个「看起来正常、但没人批准过」的排序，且它直接决定谁先挑黄金库位；容量六项是**物理约束的保守默认**，`16` §353~356 给了表值，缺席时按表值跑与文档一致。

**实现期补记（9.1 落地时）——阻断与降级的分界线，以及它在端点上的位置**：

- **① 阻断发生在「取数」这一步，故它天然是「整批」的**。`load_weights` 在组装点被调一次（不是逐单调），抛出的 `BlockedMissingPrerequisite` 在引擎之前、在任何写入之前 → 409、零方案行、零回写。**端点上没有为它加一行代码**：9.1 是把「D3 的权重行 + spec「无生效版本时阻断」」这两件已经被别处实现的事**钉上用例**，故它属验证性任务（与 8.3 / 8.4 同类）。
- **② 它与「因子级降级」必须分得开，这正是 9.x 系列存在的理由**。同一批里**缺某个因子的取值**（无快照 / 无库存 / 批号为空 / 无站台行）时引擎照常出方案、只在理由里标降级（D8；9.3、9.5 各验一处）；缺**权重**时连「该按什么比例算总分」都不知道，**没有可降级的目标** —— 按 0 权重或均分权重继续跑，会产出一份看起来正常、背后没有任何人类批准过比例的方案。故一处阻断、一处降级，不是不一致，是两类缺席的性质不同。
- **③ 提示语按成因分两种（`configured == 0` 与否）**，因为操作员的动作不同：一版都没配 = 去配一版；配了但都没到生效时间 = 等它生效，或改生效时间。用例断言的是 spec 原话那句「权重配置未就绪」而**不是逐字相等** —— 提示语里还带仓库号与排查方向，那是给人读的，不是契约（断言逐字会把「把提示语改得更清楚」变成一次需要改测试的返工）。
- **④ 测试落点**：`tests/api/test_allocate.py` 的「9.1 权重缺失 ⇒ 整批阻断」一节，造数用 `make_scenario` 的显式口径 `weights=None`（不建任何权重行 = 配置尚未就绪），判的是 `configured == 0` 这一支；另一支（已配未生效）由逻辑层的 `load_weights` 用例覆盖，不重造第二份。变异验证：让 `load_weights` 在无版本时**静默退回默认权重** ⇒ 该例红（它正是 9.1 要防的那件事）。

### D4 容量扣减不落库 —— 本阶段没有台账，就没有增量

**决策**：一次批量分配内，容量扣减只发生在**进程内的快照副本**上，不写 `AisleCap`、不写 `Snapshot`、不写 `Ledger`。第二次调用重新从 `AisleCap` 基线读起，因此**同样的入参两次调用得到完全相同的输出**。

**为什么**（三条，缺一条都不足以定案）：

1. `linkage.py` 的 `AisleCap` docstring 已钉死：「事务内增量**不落本表**：它靠 `Ledger` 同事务更新，**台账是 cap 增量的唯一来源**（`16` §6.3）」。本阶段不写台账（落位执行属 F7 / 阶段四），所以增量无处可落。
2. 落库会造出与 `Ledger` **平行的第二套 cap 增量来源**，直接撞两条红线：「台账只有一套，不新增平行台账」与「cap 与台账同事务写入必须由真实事务保证」。
3. **语义上也不该落**：分配产出的是**方案**，方案未经操作员逐单确认（L1）。把未确认的方案算进库容，等于让「未确认」产生了持久影响 —— 与「未确认不产生台账」是同一条红线的两个面。

**备选 (a)**：写一个内存外的 `cap_used` 表。被否 —— 见第 1、2 条，且 `AisleCap` 刻意没有 `cap_used` 列。
**备选 (b)**：落库但在事务末尾回滚。被否 —— 徒增写放大（SQLite 单写库），而结果与不写完全一样。

**补记（3.2 实现期）：扣减量按「整条巷道的可用量」减，不拆两个池子。**

`14` §3.4 步 3 只写「扣减该巷道容量」，**没有**说 A 类占用的是预留池还是可用部分 ——
而这两种读法会让**后一张单**看到不同的可用量。近站台巷（80 总量 / 20 预留）被 A 类吃掉
30 格后，B 类看到的可以是 `60 − 30 = 30`（都从可用部分扣），也可以是 `60 − 10 = 50`
（A 类先吃光预留池，可用部分只少 10）。

**决策**：取前者。`feasible_aisles` 收到的是「本批已占格数」这一个计数，按 `available_cap(...)
- consumed` 与判据 1 比，**不实现池子间的再分配**。理由：

- **前者在两个读法下都不越界。** 后者（先吃预留池）只是「B 类还能多拿」，即按前者算出的
  30 是**保守下界**，而不是与另一个读法并列的独立选择。取保守侧的理由与 `available_cap`
  把 `abc_class=None` 当非 A 类是同一个：破「非 A 类不占预留池」这条红线**不可追溯**
  （预留池的占用没有独立台账），而少给是可**见**的（该单降级到远巷道、走 5.2 的告警）。
- **池子怎么分是分配器的扣减口径**，不是评分侧的判据。若要实现后者，改的是 4.x / 6.x
  维护 `consumed` 的地方（按 ABC 分桶记账），不动判据 1 的写法。

口径本身（A 类到底从哪一部分扣）**未确认为业务口径**，但它的两种读法在首期只影响「B/C
能不能多拿一点」，不影响任何红线，故**不阻断本阶段**；若业务方给出口径，改一处记账即可。

**补记（8.3 实现期）：这条「不落库」的验证形态 —— 比逐列取值，不比行数。**

`tests/api/test_allocate.py::test_a_successful_batch_writes_neither_a_ledger_row_nor_a_cap_row`
断言的是「每一条 `AisleCap` 行的**每一个取值列**（含 `updated_at`）与调用前逐字相同」，
**不是**「cap 行数没变」。后者对**原地改掉 `cap_usable`** 是瞎的 —— 而那正是这条决策最现实的
失效形态：阶段四接 cap 增量时，有人顺着「分配扣减」把这一笔就地减掉，行数不变、这一版快照的
冻结值却已失真。`AisleCap.updated_at` 带 `onupdate=utcnow`，行被 UPDATE 过（哪怕改回原值）
时间戳就会动，故它是「这一行有没有**被碰过**」的证据 —— 用得上它，只是因为模型恰好带了这一列
（`17` §3.4 为漂移校正留的），不是为了多一条断言。

同一用例还要求「两条方案行在、状态停在 `PLANNED`」：**只验「没写」是不成立的** —— 一个空转、
直接返回 200 的端点同样能过前一半。两个方向都要钉，是这条红线（「未确认不产生台账」）
与普通「不该写库」的差别：它的反面不是「多写了」，而是「什么都没发生却报成功」。

### D5 四级降级链的分档：由数据源的可表达性决定，不编造阈值

`14` §3.5 / `15` §4.4 给了链的**名字**（近站台 → 次近巷道 → 远巷道 → 溢出区），但**没有给分档阈值**，也没有定义「溢出区」的物理形态。而现有数据只能表达两档：

| 档位 | 本阶段的成员判据 | 数据源 |
|---|---|---|
| 0 近站台 | `AisleCap.is_near_station IS TRUE` | 布尔列，有 |
| 1 次近巷道 | **空集** | 需要 `AisleStation.distance_weight` 的**分档阈值**，文档未给；且该表首期为空 |
| 2 远巷道 | `AisleCap.is_near_station IS FALSE` | 同档 0 |
| 3 溢出区 | **空集** | 文档称其为最后一档，但未定义它是不是 `aisles` 之外的一块区域 |

**决策**：`degradation.py` 暴露一个**档位解析器**，返回「有序的巷道分组列表」，分配器对它有 4 个位置**逐档下探**、记录首次可行的档位并写入降级原因。本阶段的解析器只填档 0 与档 2；档 1 与档 3 为空集，下探逻辑照常经过它们（空集 ⇒ 直接进下一档）。

**为什么留空而不是给个默认阈值**：分档阈值是**业务口径**（多近算「次近」？），不是工程常数。填一个数会让「为什么这单算次近」在操作员追问时答不上来，而且阈值一旦随数据分布浮动，同一天的两次分配可能给出不同档位 —— **编造一个阈值比留一个空档更糟**。档位语义与阈值一并列入待业务方确认（D14）。

**补记（5.1 实现期）：`is_near_station = NULL` 进档 2，但必须与 `False` 分开可辨。** `17` §2.1 与 `app/models/master_data.py` 第 3 条都写死了 NULL = 「权威值未到位」，**不得当 `False` 用**。解析器的处置是**两件同时成立**：① 未导出的巷道**仍进档 2**（可达、不享近站台优先）—— 丢掉它等于一次静默的候选集收缩，本可落在这条巷的单会被迫降级甚至四级走尽；② 它被**单列**在 `TierPlan.unknown_near_station` 里，供 5.2 写进 `degrade_reason`（否则操作员看到的是一条**没有成因**的降级，与 `False` 同形）。取数侧漏了这条巷（映射里没有它）走同一处置 —— 两种形态在调用侧都是「这一列的权威值没拿到」，而默认成 `False` 静默放过会把取数缺陷藏进一条看似正常的推荐里。**下游须知**：首期整表未导出 ⇒ 全部候选巷都进档 2，于是一条 A 类单的首次可行档就是档 2（远巷道），会命中「A 类降级触发告警」。5.2 的告警文案因此要把**成因**分开写（容量缺口 vs 标志未导出），不能只报一个缺口数 —— 后者会让人去「移库腾挪」而真问题是数据没导出。**档内按 `aisle_no` 文本升序**（D2 第 1 条），与入参排列无关：档内次序会影响「得分并列时选谁」（D16 的并列裁决），最终落进落库的报文。

**溢出区走尽之后**：`15` §11.1 写着「溢出区仍不可行 → 该单标记失败并提示人工介入，**不静默落位**」。所以四级走尽**不等于**降级成功 —— 该单产出「分配失败」的结果、**停留在 `PENDING`**（`15` §3.1 的 `PENDING → PENDING：批量分配失败可重试`），并提示人工介入。它不进入 `PLANNED`，也不写 `bulk_batch_no`。

### D6 「板-格」换算收在一个函数里，首期取恒等

`JobOrder.qty` 的单位未定（`tasks.md` 9.4c 登记在案），`AisleCap` 的量是**格**，`Material.cartons_per_pallet` 的单位文档也没说（`17` §2.3 只说「按单厂换算规则内置」）。而「cap 是否足够」这个判据两边都要用。

**决策**：`allocator.py` 只通过**一个**函数 `to_occupied_cells(qty, material)` 得到占用格数；本阶段该函数返回 `qty`（即**一单一位 = 一格 = 一板**的恒等），并把换算规则登记为待确认（D14）。

**为什么恒等是唯一站得住的首期读法**：`14` §2.2 的算例自己就用板做巷道容量的单位（「近站台巷道（01/02）合计剩 **100 板**」），`14` §3.5 的告警文案也是板（「近站台缺口 X **板**」），`08` §14.1 与 `CLAUDE.md` §十 的验收指标同样是板。也就是说**文档自己的算例把「板」与「格」当同一个量在用**。恒等是唯一与全部文档算例自洽、且不需要发明任何换算系数的读法；把换算隔在一个函数里，是为了规则到齐后只改一处、不动分配器。

### D7 可行巷道集的三个判据，各自的取数源

`14` §3.4 步 1 给了**三个**判据（原为四个，第四个「品质库区匹配」已按用户决定从全部文档移除，调查与处置见下）。逐个落到本阶段的取数源上：

| 判据（`14` §3.4） | 本阶段实现 | 说明 |
|---|---|---|
| `cap 足够` | `available_cap(...) >= to_occupied_cells(...)` | 见下方公式 |
| `巷道可用` | `Aisle` 主数据存在该 `aisle_no`，且该快照有对应的 `AisleCap` 行 | 见下方 |
| 非 A 类排除预留池 | 见 `available_cap` 的 ABC 分支 | — |

```
available_cap(cap: AisleCap, abc_class, now) -> int:
    if abc_class == A:               return cap.cap_total      # A 类可用含预留的总额
    if now.wall_clock >= release_at: return cap.cap_total      # 超时释放后 B/C 同享
    return cap.cap_usable                                      # 非 A 类仅可用部分
```

- **释放判定用现场墙上时间**，与 `CapacityConfig.reserved_release_at`（`Time`，当日钟点）同一时钟口径。`configuration.py` 已就此写明：按 naive UTC 比会让现场变成**次日 02:00** 释放。`now` 由路由注入（D2 第 3 条）。
- **「巷道可用」的取数源是主数据存在性，不是状态列。** `Aisle` **没有**「停用」列。备选是给 `Aisle` 加一列 —— **被否**：`17` §2.1 的字段表没有它，而 data-model 阶段已确立「**不替文档补列**」的原则（`CapacityConfig` 特意不加 `changed_by_id`、`ConversationContext` 特意不加 `updated_at`，都是同一条原则）。「停用巷道」在本阶段是一个**尚不存在的概念**，用主数据存在性表达它，含义准确且零改动。
- **`is_near_station IS NULL`（未导出）不需要特判**：预留池只在近站台非零，未导出时快照侧的 `cap_reserved` 本身就是 0，于是 `cap_usable == cap_total`，`available_cap` 自然收敛到「所有人可用全额」。**以快照三列为准**（快照是权威）；若出现「`is_near_station` 为空而 `cap_reserved > 0`」这种自相矛盾的行，仍以 `cap_*` 三列为准，并在因子级降级标记中记明。

**第四个判据「品质库区匹配」已移除（本变更的调查与处置）**：`14` §3.4 步 1 原列四个判据，第四个是这四个字，而它**全文只出现一次，且从未被定义**。文档里有两个容易被读成它的字段，但**都不是它**：

### D8 三种「降级」分开承载，一个字都不共用

「降级」在本项目有**四个**同名概念，本阶段涉及前三个（第四个属阶段四的导入回执）：

| 概念 | 含义 | 承载字段 | 出现在 |
|---|---|---|---|
| **方案级** | 容量不足，走了降级链 | `RecommendationPlan.degraded` / `degrade_reason`（**列**，带 DB CHECK） | 理由卡标题区 |
| **因子级** | 某因子数据缺失，该因子不参与评分 | `payload_json.factor_degraded`（**JSON 键**，无列） | 理由卡的因子行 |
| **排序降级** | 缺未来 N 天出库量，队列退化为仅按 ABC 排序 | `payload_json.priority.degraded` / `degrade_reason` | 队列项 |
| 导入降级链 | 导入侧的分流处置 | `ImportSession` 回执（阶段四） | 导入页 |

**决策**：列级**只承载方案级**，因子级与排序降级进 `payload_json`。这不是权宜 —— 它正好是模型已经给出的形状：`RecommendationPlan` 有 `degraded` / `degrade_reason` 两列且带 `CHECK(degrade_reason_required)`（「降级不静默」落成库层约束），而**没有** `factor_degraded` 列。给因子级补一列会让「这个方案的 `degraded=True` 到底指容量不足还是数据缺失」重新变得不可判 —— 正是 spec 里「两种降级不得混用」要拦的那件事。

**实现期补记（9.2 落地时）——`AC-002` 的第四处断言：这次下探**被记录**了**：

- **① `20` §六 `AC-002`**（「容量不足触发降级链 ⇒ 降级到次优巷道集，不崩溃、不丢弃」，边界层「分配合规」）在本阶段有四处可断言的面：降级到次优巷道集、不崩溃、不丢弃 —— 这三处既有用例已经断言 —— 以及**这次下探被记录下来**。9.2 补的是第四处，因为它落在**方案级降级这两个字段**上，正是本节管的通道。
- **② 为什么「被记录」需要独立一条用例**：`test_the_deduction_applies_to_the_next_queue_item` 只断言「第二单落到 `02`、且 `01` 不在它的候选集里」。把方案级 `degraded` 恒置为 `False`（下探照旧影响 `aisles`、只是不再记账）之后，**那条用例照样全绿** —— 现场表现是「系统推荐了远巷道，而理由卡上读不到任何原因」，「降级不静默」被违反而测试无一变红。故同一份事实要有两条用例：一条守「选对了巷道」，一条守「说了为什么」。变异验证：恒置 `degraded=False` ⇒ **只有**新用例红，旧那条仍绿 —— 缺口的形状因此是可复现的，不只是推理。
- **③ 首期「次优巷道集」就是档 2**：档 1（次近巷道）要 `distance_weight` 的分档阈值、档 3（溢出区）文档未定义物理形态，两者**空集但占位**（D5），故下探今天必然从档 0 一步落到档 2。**这不是把「次优」定义成「远巷道」**，是首期数据能表达的范围；阈值一经业务给定，档 1 自动参与，「次优」的含义随之回到文档。登记在此以免后人把用例里的 `02` 当成契约。
- **④ 两种成因的措辞**相同（本版快照里近站台就只有 5 格 vs 那 10 格被先来的单吃满），都是「近站台无可行容量」—— 有意的：理由回答「为什么没停在近站台」，不回答「谁的锅」；两者的处置确实不同（前者改配置或移库，后者是正常的批内竞争），但那属于看板的语境，不属于单条推荐理由（措辞口径见 D19）。
- **⑤ 测试落点**：`tests/logic/test_allocator.py` 新增 `test_in_batch_exhaustion_descends_and_records_the_same_degradation`（第二种成因），并在 `test_a_full_preferred_tier_descends_to_the_far_tier_and_says_why` 的 docstring 里补上 `AC-002` 编号与「四条断言各自对应场景表的哪一句话」的对照 —— 10.2 要求用例注释注明场景编号，那张对照表是它的前置。

**实现期补记（9.3 落地时）——四类输入全空：「缺哪一类」与「落在哪条通道」是两件事：**

- **① 通道对照表**（`16` §394 / `A.4` 的首期形态，9.3 的用例是它的执行版）：

  | 缺的输入 | 通道 | 为什么是这条 |
  |---|---|---|
  | `AisleCap`（cap 基线） | **逐单失败**（D19） | cap 行是**候选集的构成条件**（`AisleState` 的两半取交集）：没有 cap 行的巷道连候选都不是 —— 因子层没有可取的值，四级链也没有一档停得下来。降级的前提是「有值但不参与」，这里根本没有值（同 D3「缺权重时没有可降级的目标」那条推理） |
  | `Material.abc_class` | **因子级降级**（`abc`） | 取值未知，但有兜底顺序（单据优先、物料兜底），两侧皆空才降级；给 `0.00` 会让「ABC 未派生」与「C 类」在库里同形 |
  | `AisleStation`（巷道-站台主数据） | **因子级降级**（`station`，**方案级**粒度） | 措辞沿用 `17` §10.1 示例的「巷道-站台主数据未导出」；粒度是方案级（一条候选巷缺行 ⇒ 全部候选一并降级），故判据在 `scoring.station_degrade_reason` 而非单因子函数 |
  | `InventoryItem`（既有库位分布） | **不是降级**：合法空档案，取 `0.00` | 「数据到了且为零」与「数据没到位」是两件事（`InventoryProfile` 的 docstring / `factors.py` 第 1 条）。把空档案记成降级，会让首期**每一张**单都带一条永不消失的理由，理由就不再是信号 |

- **② 任务书那句话（「逐单因子级降级 + 四级走尽失败」）不能按字面在同一条单上同时成立**：四级走尽的单**没有 breakdown**（`AllocationFailure` 只有单号与一段文案），因子层根本没被调到。故 9.3 的用例分两段：第一段断言失败通道（每张单都在 `failures` 里、`outcomes` / `alerts` 为空），第二段在**同一份造数**上直接问 `abc_factor` / `station_degrade_reason` / `existing_factor` —— 它们问的正是分配器在那份入参上会问的同一批取数产物（`load_snapshot_index` / `load_station_weights` 都真跑）。**上表因此是本节四条通道在首期形态下的完整对照**，登记在此以免后人以为「因子级降级」也会出现在失败单上。
- **③ 造数里快照行**在**（`16` §11.6：三类文件独立导入，cap / 库存缺失 ≠ 没有快照）**：无快照那一形态归 9.5，且端点在进引擎之前就闸住（D10 补记 ② 的两层分工）。若 9.3 也把快照行拿掉，两条用例会退化成同一条，且那道端点闸门在逻辑层被绕过而无人察觉。
- **④ 本场景在端点上读不到任何理由**：`plans` 空、`degraded_alerts` 空，一句提示也没有 —— `17` §10.7 的响应没有承载 `failures` 的字段（D19 的未定项）。9.3 的验证因此只能落在引擎层，这同时是「失败原因可见」在首期的**上限**：可见 = 引擎结果里可见，不是操作员可见。
- **⑤ 测试落点**：`tests/logic/test_allocator.py` 新增 `test_the_all_empty_input_shape_fails_every_order_and_degrades_each_missing_input`（一条用例覆盖上表四条通道）。失败文案的断言与 5.3 的单测**有意重叠**：单测守措辞本身，本条守「真实取数路径上确实走到这段措辞」。成因那一条尤其要守 —— 本场景四档都是「无候选巷道」，若实现把两级成因合流成一句，操作员会被告知去腾容量，而真问题是补 cap 数据（两种成因的处置相反，D19）。

### D9 推荐理由的组装边界

`reasons.py` 按 `17` §10.1 组装 `payload_json`，并保证三条不变量（都有对应测试）：

1. **每个参与评分的因子都有取值与取值说明**；降级因子**不出现**在分解里（否则操作员会看到一个值为空的因子，误以为它参与了打分）。
2. **`scores[巷道]` 恒等于「可用因子加权和 ÷ 可用因子权重之和」**（两位小数）。`17` §10.1 已论证：权重和不等于 1 时这个归一化是纯比例缩放，不改变同一次运行内的相对次序。
3. **列与 JSON 不打架**：`RecommendationPlan.degraded` / `degrade_reason` 与 `payload_json` 里的同名字段是**同一次写入的投影**，必须一致（`RecommendationPlan` 的 docstring 已把这层关系写明）。因子级降级**只在 JSON 里**，不投影成列。

「预测跨巷道」由分配器在**全部队列处理完后回溯**计算（`14` §3.4 步 5）：`| 既有快照中该物料占用的巷道 ∪ 本次分配给该物料的巷道 |`，阈值取 `CapacityConfig.same_material_cross_aisle_threshold`（默认 5）。既有占用的取数 = 当前快照的 `InventoryItem` 中该 `material_code` 的行按 `substr(location_code, 1, 2)` 去重 —— 切片而非数值化，`CLAUDE.md` §七。**同批跨巷道不预测** —— 本期的契约范围，不是时点所限（批号在入库单建立时已由系统按生产批生成，分配时刻本可聚合；2026-09-11 更正）。

**实现期补记（7.1 / 7.2 落地时）——组装由谁调、既有占用怎么取**：

### D10 端点契约与权限口径

`POST /api/allocate/batch`，请求体 `{warehouse_id, snapshot_version?, job_order_ids[]}`（`17` §10.7）。

- **`job_order_ids` 必填、无隐含默认**。不设「空即全量」：那会让同一份数据按调用方的不同意图产出不同结果，直接撞「同样输入必得同样输出」。空数组 = 明确的空集，产出空 `plans`。
- **单次上限 50 单**，超出拒绝并提示拆分，**不静默截断**（静默截断会让调用方以为 51 单都分配了）。
- 只处理 `PENDING`，其余状态**整体拒绝**（不部分成功）。不新增 `PLANNED → PLANNED` 等未定义迁移。成功者写 `bulk_batch_no` 并迁 `PLANNED`。
- 响应 `plans` 按 `priority` 降序；`plan_id` 指向 `RecommendationPlan`，**理由体按 `plan_id` 另取**，不在响应里复制一份（避免同一份理由有两个可能分叉的副本）。
- `snapshot_version` 出参是 `Snapshot.snapshot_time` 的 `"%Y-%m-%dT%H:%M"` **渲染**（`17` §10.7 的展示形状）。**不要把 `Snapshot.version_no` 塞进它** —— `Snapshot` 的 docstring 已写明存储层用 `id` 作被引用键、时间戳串只作展示。

**权限**（design rule：写明 `resource.action` 并对照 `13` 的矩阵）：

- 资源标识 = **`inbound.operate`**（该端点由入库作业的批量分配动作触发）。
- `app/api/permissions.py` 的 `ROLE_PERMISSIONS` 对照：`warehouse_keeper` ✅、`admin` ✅（`AUTO_ONLY` 之外的全集）；`planner` ❌、`supervisor` ❌（矩阵里主管**没有** `inbound.view`，注释明写「入库执行不归主管」）。
- **`engine.invoke` ∈ `AUTO_ONLY`（`permissions.py:75`），恒不授予任何角色**，且 `check()` 里这条判断**先于**查表。故「引擎调用本身不向任何角色暴露」是**代码已保证的事实**，不是本阶段新增的约束。文档 `27` 的「仅授权角色」表述与此冲突，以 `13` + `CLAUDE.md` 为准（已订正，见 D13）。
- **本阶段不挂 403**：`permission` 规格的「v1 不做端点级资源鉴权」仍然有效，越权由角色菜单可见性 + 二次确认承担。本端点的 **401 由既有认证中间件覆盖**，引擎侧零新增鉴权代码。
- **已订正 `permission` 主规格的表述**（2026-09-11，按用户决定）。原条「自动写权限封闭」的正文写「任何角色都不得通过手动入口触发台账写入或引擎调用」，其场景更直言「不存在面向角色的手动触发端点」—— 本端点恰恰是持 `inbound.operate` 的角色**可调**、且**会触发引擎**的，字面上正面冲突。

  订正**不改实质**（`engine.invoke` 恒不授予这条，`AUTO_ONLY` + `check()` 先于查表已保证），只把口径从**端点级绝对**收回**资源级**：不得以 `ledger` / `engine` 为**目标资源**设手动接口，而引擎调用作为**业务动作的内部后果**发生、授权依据是该业务动作的资源标识。依据是 `13` §2.2 的 `engine` 行原文「`invoke`（系统内部调用，**不向业务角色开放手动触发**）」与同节图例「自动 = 由作业流 / 引擎自动执行，不向角色暴露手动入口」—— 两条讲的都是**资源不得被授予**，不是「系统不存在任何会触发引擎的端点」。

  落地在 `specs/permission/spec.md` 的 `MODIFIED Requirements`：携带整条需求（正文订正 + 两条原场景保留，其中「引擎调用无手动入口」的 THEN 收紧为「不存在以 `engine` 为**目标资源**的端点」）+ **一条新场景**「业务动作间接触发引擎不算手动入口」固化这个读法。**主规格要到归档时由 delta 同步** —— 在此之前 `openspec/specs/permission/spec.md` 仍是旧措辞，这是 OpenSpec 的正常时序，不是遗漏（见 Risks）。

**实现期补记（8.1 落地时）——D10 没点名、但端点必须自己定的四件事**：

- **① 作业单在报文里的身份 = `str(JobOrder.id)`**，端点以 `^[1-9]\d*$` 拦下非规范形式（前导零、`+`、小数、空串）。**这不是洁癖**：`order_queue` / `build_priorities` 的重号检查 / 引擎内的扣减索引三处**都按字符串**做键，若放 `"007"` 进来，同一条 `JobOrder` 会以两个身份同时入队、被两次扣减，而全程**没有任何一处会报错** —— 产出的是一份看起来正常的方案，只是那条单被算了两次。线上标识从此是「规范十进制的 id 串」。
  - **一个连带后果，登记以免日后当成 bug**：D2 的排队 tiebreak `job_order_id 升序` 实际落在**十进制串的字典序**上（`"10" < "9"`）。它仍然**确定**（D2 要的就是确定性，不是数值序），但读队列顺序时不要按数值大小去预期。
  - `17` §10.7 的示例把 id 写成裸数字，故**数字与串两种形状都收**：Pydantic 侧用 `str` 并显式覆盖 JSON 里的整型，端点只认规范化后的串。
- **②「当前快照」= 该仓库 `version_no` 最大者**（`pick_current_version`），不自造「最新 = 导入时间最晚」这类第二条口径。**无 `Snapshot` 行 ⇒ 端点 409 `blocked_missing_prerequisite`**。这处要与 9.5 分开读，两层各管一半：
  - **引擎层照常分配**：`load_snapshot_index(session, snapshot_id=None)` 收 `None` ⇒ `SnapshotIndex.absent` ⇒ 三个库存因子降级，**不阻断** —— 9.5 在 `tests/logic/` 验的就是这一半（「无 `Snapshot` 行时分配照常完成且理由标注降级」）。
  - **端点在进引擎之前闸住**，两条理由：(a) `snapshot_version` 是契约里的**必填**出参且带 `"%Y-%m-%dT%H:%M"` 的 pattern，它唯一诚实的来源就是 `Snapshot.snapshot_time`，没有快照行就没有东西可渲染，而 D10 明写**不许**拿 `version_no` 去顶；(b) `AisleCap` 按快照存，无快照 ⇒ 可行巷道集恒空 ⇒ 队列里**每一条**单都会走完四级降级链，把一句「数据还没准备好」记成 N 条「分配不出来」的方案，还都会落库。**阻断是「不猜落位」**（`CLAUDE.md` §四），不是新增约束。
  - 与 spec 第 143 行 / 9.5 的字面不冲突：那两句说的是**入库流程**的分配照常完成（`CLAUDE.md` §四把快照缺失的阻断限定在**出库**）。本端点是入库侧的批量分配，但它**不产生落位写入**（8.3：无台账、无 cap 写），故这里的阻断只是拒绝生成一份无依据的方案，不属于「出库阻断」那一类。登记在此，若阶段四的入库流需要「无快照也出方案」，改动点在**本端点**而不是引擎。
- **③ 三种拒绝各自的错误类别**（D10 / D17 只写了「拒绝」，没点类别）：未知 id、同批重号、非规范形式 ⇒ `ValidationBlocked`（422）；声明的 `snapshot_version` 与实际不符 ⇒ `StateConflict`（409）；无快照 ⇒ `BlockedMissingPrerequisite`（409）。前三条**必须在进引擎之前**拦 —— 放进去会撞 `build_priorities` 的裸 `ValueError`，以 500 的形式泄出去（一个用户输错的 id 不该表现成服务端故障）。四条拒绝路径都验了**零方案行落库**。
- **④ `outbound_qty` 在阶段三恒为 `None`**（排序降级）：本期无出库数据（导入管线属阶段四）。取 `None` 而**不是 `0`** —— `0` 会被 `ABC_ONLY_WEIGHTS` 之外的处理读成「有出库量，且为零」，那是一个**本不存在的观测**；`None` 才是「这项数据本期没有」。
- **⑤ 容量配置缺席时退回 `Settings` 引导值**（D3 的落点）：`pick_current_version` 选生效行，无生效行 ⇒ `reserve_release_at="18:00"` / `same_material_cross_aisle_max=5`。退回逻辑放在**组装点**而不是引擎 —— 引擎刻意不认识 `Settings`（`app/core/config.py` 是装配层的东西），把它拉进 `engine/` 会让「引擎只认传入的配置」这条边失效。
- **⑥ 本阶段只写 `RecommendationPlan`**：状态迁移（`PENDING → PLANNED`）与 `bulk_batch_no` 回写是 **8.2**。故 8.1 的测试**刻意不断言**已分配单的 `status` —— 那会把 8.2 的行为提前钉死在本用例里。

**实现期补记（8.2 落地时）——状态迁移与批次号回写落在哪一步**：

- **① 非 `PENDING` 是整批拒绝，判在进引擎之前**。本条的「整体拒绝（不部分成功）」有两种实现位置：写在写入循环里逐单判，或整批预检。**取整批预检**（`_require_pending`，紧接 `_load_orders` 之后）—— 逐单判的形态是「前几张写、后几张拒」，一个 `StateConflict` 抛在循环中间时前面几张已经 `session.add` 了，虽然整批回滚仍是「零写入」，但它把「整批拒绝」这件事**押在「调用方一定不 commit 中间态」上**。预检不押这个。报**全部**越界单而不是第一张：调用方要一次把集合改对。判决放在引擎之前也是同一原则 —— 整批拒绝不该依赖「引擎恰好没出方案」这个巧合。
- **② 回写的判据 = 「这一单在 `batch.outcomes` 里」**（出了方案的才算成功者）：四级走尽、只出现在 `batch.failures` 里的单**停留 `PENDING`、不领批次号**。这与 D12 的「该单停留 `PENDING`、提示人工介入」是同一件事的两种读法 —— 失败单若也写上批次号，「这单属于 `BAT-xxx` 批」在追溯时就是假话，且它同时不再是「可重试的待分配单」（`PENDING → PENDING` 是 `15` §3.1 那条合法自环）。实现上它不是额外的一个判断：回写就写在「逐单组装理由并落行」那个循环里，**与落行同一条判据** —— 于是「在 `plans` 里」和「被回写了」不会分叉。
- **③ 迁移走共用状态机，版本跟着走（D1）**。`order.status = assert_transition(order.status, PLANNED)` + `bump_lock_version(order, expected=order.lock_version)`。两点要分开读：
  - 那条 `assert_transition` 在今天是**必然通过**的（预检已整批把过一道）。它守的是**另一件事**：将来若有人放宽预检（比如改成「跳过非 PENDING」），非法迁移会在写入处当场报错，而不是静悄悄写出一行 `CANCELLED → PLANNED` —— `state_machine` 的「不新增未定义迁移」正是要拦这个。
  - **请求里没有版本号**（D10 的请求体只有三项），故「重复提交同一批、第二次必被拒」是**状态守卫**兑现的，不是版本比对。推进 `lock_version` 保的不是本次调用，而是**下一个**带着版本来的调用方（二次确认卡）—— 行变了而版本没变，那边会以为自己读到的还是旧内容，而那正是 D1 要防的静默覆盖。据此，`bump_lock_version` 里那个必然通过的比对是「增量语义只有一处定义」的代价，不是一次校验。
- **④ 409 的 `detail` 形状定死**：`{"not_pending": [{"job_order_id": "<线上形态的 id>", "status": "<JobStatus 取值>"}], "expected": "PENDING"}`，按 id 数值序排列。`errors.error_body` 把 `detail` 原样透出，前端拦截器按 `error`（`state_conflict`）分流；若这里只给一句自然语言，前端要判「这一批里哪几张要剔除」就只剩拆字符串一条路。**排列顺序也定死**（数值序，不是串的字典序）：顺序不定会让同一批两次调用给出两份顺序不同的明细。
- **测试落点**：同一文件的「8.2 状态迁移与批次号回写」一节 —— 4 条用例 / 6 个参数化形态（回写与响应一致 + `lock_version` 推进 + 未提交单三件不动；三个非 `PENDING` 状态各自整批拒绝且零写入；失败单不被回写且不占容量；重复提交第二次被拒且不新增方案行）。**单跑全绿，故另做变异验证**（去掉预检 ⇒ 4 例红；不推进版本 ⇒ 1 例红；回写别的批次号 ⇒ 3 例红；迁到 `PENDING` 自环 ⇒ 3 例红），改回后 `diff` 确认与验证过的版本逐字相同。8.3 / 8.4 / 8.5 仍未测，各归本主。

**实现期补记（8.4 落地时）——401 是中间件的、403 在本阶段不存在**：

- **① 401 归中间件，端点上没有一行是 8.4 加的**。8.4 的验证条件是「有 401 用例」而不是「实现 401」：`AuthMiddleware` 早已对 `/api/*` 全局校验（`middleware.py` 的模块 docstring 即 13 §6.1 第 1 层）。四个形态各测一遍 —— 缺 `Authorization` 头、只有方案名没有凭据、凭据不是 JWT、签名被改过：它们走中间件里**四条不同的分支**（`_extract_token` 的两个早退、`decode_session_token` 的解析失败、签名校验失败），收敛到同一个 401。**一条不够**：少测哪条，那条就可能被顺手改成放行而没人发现，而这四条都是「不认证也能进来」的入口。
- **② 用例断言的是「端点整个没跑」，不只是状态码**。401 由中间件在路由之前返回；一个把鉴权写在端点内部（先取数、再检查）的实现**同样回 401**，但库里的方案行与作业单已经动过了。故除状态码与 `error == "unauthenticated"` 外，还断言 `plan_rows() == ()` 且全部作业单仍 `PENDING`、`bulk_batch_no is None`（8.2 的两处回写都没发生）。变异验证：让 `_requires_auth` 恒 `False`（等于把中间件摘掉）⇒ 该例红。

**实现期补记（8.5 落地时）——上限怎么判、空批算什么**：

- **① 超限走 `ValidationBlocked`（422），`detail = {"submitted", "max"}`**。它是**报文错误**（调用方改报文就能过），与「未知单号」「形状不合法」同类；故响应体形状与其他 4xx 一致（`{"error", "message"}` + `detail`），前端拦截器不必为它单开一个分支。
- **② 判在原始条数上，不是去重后的条数** —— 本条唯一的取舍，两种读法都能自圆其说，故把取谁的理由写死：`_requested_ids` 会去重，若先去重再判长度，一份 60 条里带 10 条重号的请求会以「实为 50 条」被放行，那依然是**静默削减**，只是削减发生在去重那一步。去重是防「同一张单被扣两次」的**正确性**检查，不该顺带承担规模上限。规格的措辞也站在原始条数这一边（「请求提交了 51 条单据号」）。用例 `test_the_limit_counts_what_was_submitted_not_the_deduplicated_set` 钉这条。
- **③ 也正因如此，上限不能写成 `job_order_ids` 上的 `Field(max_length=...)`** —— 这一条 8.5 落地时是**删掉一行**而不是加一行：8.1 在字段上留了 `max_length=MAX_JOB_ORDERS_PER_BATCH`，而常量处的 docstring 早就写着「不写成 `Field(...)`」，两者自相矛盾。删它的理由有两条，缺一不可：(a) Pydantic 层的 422 是**另一种响应体**（FastAPI 默认的 `{"detail": [...]}`，没有 `error` / `message`），而本端点把领域错误的形状统一在 `errors.error_body` 上；(b) 文档要的是「拒绝并**提示拆分**」，通用文案不会叫调用方去拆分。**留着的危害恰恰是它不报错**：超限照样被拒，只是拿到另一种 422 形状 —— 8.5 的用例首跑红在 `KeyError: 'error'`，抓的就是这一行。
- **④ 判决次序：整体的先于逐条的**（上限 → 形状 → 重号），且都在取数之前。组内次序不是任意的：上限问的是「这一批能不能受理」，形状与重号问的是「里面哪一条不对」。**同一个 422 之下有两条路径，故用例断言 `detail` 而不只断言 `error`** —— 状态码相同的两条路径，靠状态码分不出来（把长度检查挪到取数之后，回的就是「未知单号」那个 422）。
- **⑤ 空数组 = 明确的空集，仍是一次成功的往返**。产出空 `plans` / 空 `degraded_alerts`、零方案行、零回写；`bulk_batch_no` 与 `snapshot_version` 照常回显（契约把两者定成必填，而「这一批用了哪一版快照」对一次空批同样可答 —— 就是当前快照）。**空批不消耗批次号**：D11 的 `NN` 是「当日**已有**号的数量 + 1」，是**计数**不是**计数器**，无号被领走则序号不前移，连调两次拿到同一个串 —— 这是 D2 的直读，不是「两次撞了号」的 bug（空批没有成员，没有 `JobOrder` 会领走它）。
- **⑥ 测试落点**：同一文件的「8.5 规模上限与空批」一节 —— 3 条用例（51 单被拒且零方案零回写；51 条里带一条重号同样被拒且 `detail` 证明判的是原始条数；空数组产出空 `plans` 且不消耗批次号）。任务书只点名两条用例，第三条是**为②那条取舍补的**（取舍由实现定下，就得有可执行的证据，否则下一个人只看到一行代码和一句注释）。**变异验证 4 处**：去掉长度检查 ⇒ 2 例红；把检查挪到取数之后 ⇒ 2 例红；改判去重后的条数 ⇒ 1 例红（**恰是**钉这条取舍的那一例）；把空数组读成「全量」⇒ 1 例红（**恰是**空批那一例）。四处改回后 `diff` 确认与验证过的版本逐字相同。

### D11 批量批次号的生成规则

`BAT-<现场日期 YYYYMMDD>-<当日序数 NN>`（形状取自 `17` §10.7 的示例 `BAT-20260908-01`）。`NN` = 当日已有批次号的数量 + 1，在同一事务内由 `JobOrder.bulk_batch_no` 的日期前缀计数得出。

- **日期用现场日期**，不是 naive UTC —— 沿用 `CapacityConfig.reserved_release_at` 已经立下的口径：给现场看的「当日」= 现场墙上时间的那一天（`18:00` 指现场的 18:00）。
- 规则必须**确定**（D2）：不能用 `uuid4`、不能用随机后缀。同一份入参两次调用应得到同一个批次号 —— 第二次会因为前一次的 `JobOrder.bulk_batch_no` 已回写而得到 `NN+1`，这是**入参已变**（作业单状态不再是 `PENDING`，第二次会被拒），不是不确定。
- `bulk_batch_no` **不是唯一键**（模型没有给它唯一约束）—— 它是追溯用的分组标签，不是业务主键，故不为它加约束。

| 失败 | 影响面 | 恢复 |

### D17 时钟口径：`now` 是**现场墙上时间**（业务钟），与审计钟分开（实现期补记）

**起因**：3.1 落 `available_cap` 的释放判定时，两处事实来源对不上，而 **D2 第 3 条只注入一个 `now`**：

- `app/core/config_version.py:_require_awareness` 的报错文案教调用方这样转：`datetime.now().astimezone().replace(tzinfo=None)` —— 那是**本地墙上时间**；
- `app/models/configuration.py` 的两处注释（`WeightConfig.effective_at` / `CapacityConfig.effective_at`）写的是「**naive UTC**，与 `created_at` 同一口径」。

同一个入参不可能同时是两种钟（本机 UTC+8 差 8 小时），而它两头都要用：`pick_current_version`（D3/D4）比 `effective_at`，释放判定（D7）比 `reserved_release_at`。

**判据（分界其实已经立下了，只是没写在一处）**：D7 明写「释放判定用**现场墙上时间**」，D11 明写批次号的日期「用**现场日期**，不是 naive UTC —— 沿用 `CapacityConfig.reserved_release_at` 已经立下的口径」。两者给出的是同一条分界：

| 钟 | 列 | 谁读 | 为什么 |
|---|---|---|---|
| **业务钟**：现场墙上时间（naive） | `reserved_release_at`、`effective_at` | 引擎（本变更）、操作员 | 「当日 18:00 释放」「预约 9/12 08:00 生效」都是给**现场**看的话；按 UTC 比会变成次日 02:00（`configuration.py` 原文已就此论证过 `reserved_release_at`） |
| **审计钟**：naive UTC | `created_at` / `updated_at` | 审计与展示 | 「这行什么时候写的」是**机器**口径，与现场钟点无关（`base.py` 的 `utcnow`） |

`effective_at` 归业务钟：它回答的是「**预约什么时候生效**」（`17` §七 的「可预约生效」），与「当日 18:00 释放」是同一类问题 —— 而它在模型注释里被写成 UTC，是阶段二**尚未区分这两类钟**时的措辞。

**决策**：`now` = **现场墙上时间**（naive；调用侧 `datetime.now().astimezone().replace(tzinfo=None)`），全引擎一个入参，不做任何内部换算。`reserved_release_at` / `effective_at` / 批次号日期按它读；`created_at` / `updated_at` 引擎不读，故两者不并存于一次计算。

**已落**：订正 `configuration.py` 的两处注释（**注释级改动**，无列、无约束、无迁移）。**无行为变化**：全仓没有任何写入方用 `utcnow()` 写 `effective_at` —— `scripts/seed_dev.py` 与各测试传的都是字面量，故「原本按 UTC 存的那些行」并不存在。实现侧不需改动：`load_weights`（2.3）与 `available_cap`（3.1）都直接收这个 `now`，与 `pick_current_version` 的契约（两侧同钟）自洽。

**2026-09-12：守卫提到一处共用**。3.1 的 `reserved._require_wall_clock` 与 6.3 的批次号日期要的是**同一个判据**（`tasks.md` 3.1 的补记已预告「到那时把它提到一处共用，不要复制第三份」），故落在 **`app/core/clock.py::require_wall_clock(now, *, purpose)`**：`purpose` 说明这一处拿 `now` 做什么（「预留池的释放钟点」/「批次号的现场日期」），报错时读的人才知道是哪个判据在拒。放 `app/core/` 而不是 `engine/` 里：那是横切关注点的家（`CLAUDE.md` §三），**引擎七个模块之间因此不多出一条依赖边**（D1 的调用链是一条单向图，为借一个守卫塞进 `reasons → reserved` 会把那张图读乱）。`reserved.py` 改为 import 它，行为不变（`test_reserved.py` 那条 aware 断言按新消息微调措辞，判据一字未动）。

### D18 优先级三项的归一化口径与「排序降级」的作用域（实现期补记）

**起因**：`14` §3.2 给了三项加法的**式子**（`priority = w1 · 未来N天交货单出库量(归一化) + w2 · ABC等级分 + w3 · 既有集中度增益`）与一句「ABC 只分三档、**同档内不排序**」，但**三处都没给**：① 三项各自的归一化分母，② 系数取值（D14 已登记为等权），③ 缺数据时降级的作用域（整批还是逐单）。而 `17` §10.1 的 `priority` 示例**给不出反推证据** —— 它的三项取值与总分本身不自洽（已按铁律先改正本，见本节末）。故沿用 D16 的同一手法：**能给证据的给证据，给不出证据的明说「本条无示例可反推」，并把口径钉在一个可替换的单点上。**

| 项 | 本阶段口径 | 依据 / 反推证据 |
|---|---|---|
| `abc` | 等级分 ÷ 3（A = `1.00` / B = `0.67` / C = `0.33`）；`None` ⇒ `0.00` | **有证据**：`17` §10.1 的 `abc: 1.00` 与该单为 A 类自洽，且与 6 因子里的 `abc` 同一套（`14` §3.2 的 A=3 / B=2 / C=1）。复用 `factors.py` 的等级分常量，不写第二份。`None ⇒ 0.00` 取**保守侧**：未知档不排到 C 类之前；「未知不得静默放行」那条红线由 `D7` 的 ABC 分支（预留池）把守，两处各管一段 |
| `outbound_qty` | 本单该物料的未来 N 天交货单出库量 ÷ **本批队列中该量的最大值** | **无示例可反推**（三项示例值本身不自洽）。队列内最大值是**唯一不需要编造常数**的分母（D5 的同一条原则：编造阈值比留空更糟）；同批共享一个分母 ⇒ 「同档内按出库量降序」的序不变，而跨批不可比 —— 这与 `priority` 的用途一致（它是**当日队列内**的「谁先挑」）。「未来 N 天」的 N 在 D14 登记 |
| `existing_gain` | 该物料在快照里已有占用巷道 ⇒ `1.00`，否则 `0.00` | **无示例可反推**（示例的 `0.30` 同样反推不出）。「并回既有巷道可降跨巷道数的幅度」**可归一化的读法只有二值**：能并回（跨巷道数不因本单增加）/ 不能。不采 `1/(k+1)`（对 k **递减** —— 越散的物料越先挑，与「收拢」反向）；不采 `k/(k+1)`（多一个未定口径）。形态与 `batch` 因子的二值同类 |

**系数的常量**：`DEFAULT_PRIORITY_WEIGHTS = (1/3, 1/3, 1/3)`（D14 的「一处常量元组」），另有两个降级态的取值 `ABC_ONLY_WEIGHTS = (0, 1, 0)`（缺出库量）与 `NO_ABC_WEIGHTS = (1/3, 0, 1/3)`（ABC 未派生）—— 三者形态相同、都只是系数元组，故「退化」不需要第二条算术路径。三项权重合为 `1` ⇒ `score ∈ [0,1]`，与 `terms` 各项同域（系数按**权重和**归一化，故业务方给 `(5,3,2)` 这类相对值时域不变）。

**`score` 不做两位数量化**（与 `scores` 有意不同）：`17` §10.1 的两位小数口径只写给 `scores`；把 `priority` 也量化到两位，会让「同档内按出库量降序」在差 < 0.005 的两单上**并成一档**、落到 4.3 的 `job_order_id` 兜底 —— 而用出库量把同档拆开正是 `14` §3.2 要它做的事。量化在这里是**丢信息**。

**「排序降级」的作用域 = 整批**（4.2 落地）：任一队列项缺 `outbound_qty` ⇒ **全队列**退化为仅按 ABC，且**每一项**的 `priority.degraded` 都为 true。两条论证：① `14` §6.2 说的是「**排序**退化为仅按 ABC」—— 降级的是排序规则本身，不是某一项的分数；② 同一批里一部分按三项排、一部分按一项排，得到的序**没有意义**（不同刻度不可比）。与 `station` 因子「一条候选巷缺行 ⇒ 全候选一并降级」是同一条论证（D16）。

**降级只换一组系数、不另开算式**（4.2 落地）：`ABC_ONLY_WEIGHTS = (0, 1, 0)` 仍走 `score_priority` 同一段算术 —— `17` §10.1 的「`score` 是三项的加权和」在降级态下依然成立（此时 `score` 恒等于 `terms.abc`，一眼可复核），不为降级单开一条分支。集中度增益**一并**退出排序：`14` §6.2 退化的对象是**排序键**（不是「去掉缺的那一项」），且缺这份数据的场景里现场站得住的判据只剩 ABC 档 —— 让散料凭「能并回既有巷道」插到 A 类之前，与「同档内不排序」直接冲突。

**「ABC 未派生」的处置是本次实现期补的口径，`14` §6.2 未写**（`abc_term` 对未知档返回 `0.00`，故这里必须决定它算不算降级）：**任一队列项两侧都无 ABC ⇒ 该分量在全部队列项上计 `0.00`**（系数 `NO_ABC_WEIGHTS = (1/3, 0, 1/3)`，按权重和重新归一化 —— `score_aisles` 丢弃降级因子的同一手法），且 `degraded=true` + 原因写明。理由与上面那条同源：只把出事的那几条计零，同批又会一半按真实等级、一半按 `0.00` 排，同样是**混刻度**。代价是 ABC 这一项对本批无信息 —— 那正是「数据没到」的真相，而 `degraded` 与原因把它说出来，免得 `0.00` 被当成一个算出来的值。**未定项**：`14` §6.2 只把「缺出库量」写成降级，ABC 未派生要不要单列一类 `degrade_reason`（供前端分别渲染「去补成品清单的哪一步」）留待业务口径确认；本阶段两种情形共用同一通道，原因文案里分句写明。

**`terms` 记事实、`score` 记本批实际用的排序键**（4.2 落地）：部分缺失时两者故意不一致 —— 有出库量的那几条仍写自己的归一化值（把真实值抹成 `0.00` 去凑一个自洽的等式，会掩盖「这份数据其实有」，比不一致更糟），缺的写 `0.00`（「没有这份数据」为真）；差异由 `degrade_reason` 解释，那正是留给复核者的入口。

**N 的常量不在 4.2 落**：D14 把「未来 N 天」的 N 排给 `priority.py`，任务 1.2 又要求把四个待确认默认值**集中**成具名常量。为避免两处各写一份，4.2 的降级文案**沿用 `14` §6.2 的原文术语**（「未来 N 天交货单出库量」），不在这里编一个天数；N 的唯一定义点与 `TODO` 随 1.2 落。

### D19 降级文案的三个口径与「四级走尽」的对外出口（实现期补记）

**起因**：`14` §3.5 给了告警文案的一半（「近站台缺口 X 板，建议移库腾挪」）与两条要求（每步记录降级原因、A 类爆款被迫降级触发告警），但没给：① X 怎么算，② 触发面到哪一档为止，③ 四级走尽后失败单的**原因**从哪里对外（`17` §10.7 的响应只有 `plans` 与 `degraded_alerts`）。

| 项 | 本阶段口径 | 依据 / 取舍 |
|---|---|---|
| 缺口量 X | `max(0, 本单需量 − 近站台剩余可用)` | 差额而不是整单需量：主管据此决定是否移库腾挪，缺 2 板与缺 20 板处置不同；报整单会把这句指令变成「永远缺一整单」。spec 的示例（缺口 12 板）与差额读法自洽 |
| 告警触发面 | **A 类** ∩ 停在**档 2 / 档 3** | `14` §3.5「若 **A 类爆款**被迫降级到**远巷道**」+ spec 的「降级至远巷道或溢出区」。两个方向都必须收紧：放宽到任何降级 ⇒ 每条 B/C 单都告警。`abc_class = None` **不告警** —— 未知档不是 A 类（`Material.abc_class` 的同一条：不得静默当好料） |
| 文案的**成因**句 | 三种成因分开写（未导出 / 本快照无近站台巷道 / 容量不足） | **本次实现期加的，且是必需的**：首期整表未导出 ⇒ 每条 A 类单的首次可行档就是档 2，这条告警会**天天**触发；若只说缺口，主管会去腾容量，而真问题是巷道主数据没导出（`16` §394 的预期状态）。`「近站台缺口 X 板，建议移库腾挪」` 半句仍**逐字**照抄（spec 逐字要求，它是操作指令，同义句就不是同一句指令） |

**「近站台剩余可用」的生产者与口径**（2026-09-12，随 tasks 6.1 补记）：上表只定了缺口量的**公式**，没定「剩余可用」由谁算、按哪个集合算。裁定落在分配器 `_alert_for`：

- **按本单的候选集算，不按全仓近站台巷道** —— 取「**这一单**能从近站台拿到多少」，因为 `available_cap` 对 A 类与非 A 类给的数不同（预留池），同一时刻两条单的「剩余」本来就不是同一个数；
- **逐条按 0 保底再相加**（`Σ max(0, available_cap(...) − 已占)`）：单条巷道的余额不可能为负，而负数会把缺口报大 —— 一条发给主管的错数字没人复核得出来（`degradation.near_station_gap` 对负剩余当场报错，同一条理由）；
- **扣 `consumed`，且在扣减落点写回之前取**：缺口说的是「这条单准备落位时近站台还剩多少」，含它自己刚占的那部分会让主管看到一个比现场小的缺口。停档 ≥ 2 时两条路径恰好相等（本单没落在任何近站台巷道），顺序在这里是为了**不依赖那个巧合**。

这也是 5.2 的 `is_alarming` / `near_station_alert_message` 唯一的调用点 —— 在此之前它们只有定义没有消费方。

**「四级走尽」不是降级成功**：链的末端没有「再往下」的档，把它记成一次降级会让它在后验里与「降级到远巷道」同形 —— 后者是正常结果，前者是待人工处理的失败。故失败单单独成类（`AllocationFailure`：**只有单据号与可展示文案，没有巷道**），它因此也**塞不进 `degraded_alerts`**（`DegradedAlert.aisle` 是必填的 `min_length=1`，`17` §10.7）—— 这是刻意的：给失败单编一条巷道，等于产出一条「落在某条不存在的巷道」的记录，而落位正是红线里绝不静默的那一步。AC-005 的「不静默落位到非法巷道」在数据结构上就由「没有巷道字段」兑现。

**未定项（需业务/前端口径确认，本变更不擅自改契约）**：`17` §10.7 的响应**没有承载「分配失败」的字段**，故失败单目前的对外信号是「**不在 `plans` 里** + 状态仍 `PENDING`（`15` §3.1 可重试）」，而失败原因（含「请人工介入」）只存在于引擎结果与日志里 —— 操作员在端点响应里看不到它。两种可选补法都动契约：给 §10.7 加 `failures[]`（形状如 `{job_order_id, message}`），或复用 `degraded_alerts` 并放开 `aisle` 必填（不推荐：那会让「失败」与「降级」共用一个出口，与 D8「两种降级分开承载」的立场相反）。**留待确认**；本阶段按「不进 `plans`」实现，失败原因在 `POST /api/allocate/batch` 的响应之外由引擎结果携带（8.x 落地时一并登记）。

**这个未定项的首期后果（9.3 落地时补）**：四类输入全空是**阶段三现场的真实形态**，此时**每一张**单都走完四级链 ⇒ 端点上返回的是一份**空 `plans` 且零告警**的成功响应，操作员从报文里读不到「为什么一张也没出来」。这不是本变更引入的缺口（契约里本就没有那个字段），但它把上面这个未定项的**代价**摆明了：在首期，端点的应答与「今天没有待分配的单」在形态上完全一样。故 9.3 的验收只能落在引擎层（D8 的补记 ④ 已登记「失败原因可见」的上限）。

**档位解析器的入参是候选集、不是可行集**（5.1 落地时的接口裁定）：`resolve_tiers` 收 `master ∩ caps`（判据 2/3 过关），容量由下探方逐档判。若传可行集，每一档的成员都只剩「塞得下的那些」，空档于是有两个含义（本来没有这类巷道 / 有但容量不足）而无法分辨 —— 而这两种成因的处置完全不同（补数据 vs 腾容量），`tier_stop_reason` 与 `allocation_failure` 的文案都要分开写。

## Risks / Trade-offs

- [**首期无真实数据，评分质量无法验证**] → 这不是风险而是既定安排（`16` §394）；本阶段验收的是**算法本体的正确性与可追溯性**（造数断言 + 理由可复算），数据侧的验收在阶段四/六。明确不声称「推荐质量已达标」。
- [**「次近/远/溢出区」留空 ⇒ 降级链实际只有两档**，与 `14` §3.5 的字面四档不符] → 链的**结构**是四档且逐档下探（空档直接跳过），字面差异只在档位成员上；D5 已论证「编造阈值比留空更糟」。**如实报告**，不声称四级已全通。
- [**恒等换算使 cap 判断在真实数据下会偏**] → 隔离在 `to_occupied_cells()` 一个函数体；规则到齐前，所有 cap 数值都是**同一口径下的相对比较**（本次批量内部的竞争关系正确，绝对可行性待定）。已在 D14 登记。
- [**内存扣减 + 不落库 ⇒ 两次并发调用会各自看到全额容量**] → 单进程单写（`CLAUDE.md` §四），且本阶段分配不产生持久影响（未确认不落库）。真正的容量竞争一致性属 F7 落位执行（阶段四，与台账同事务 + 乐观锁）。
- [**`Decimal(str(x))` 量化在极小数上有可观误差**] → 只用于**展示与比较**两位小数，不用于累加；累加走浮点、比较走量化后值（D2 第 2 条）。测试期望值**必须避开恰好落在半值上的数**（`17` §10.1 已就此写明）。
- [**`snapshot_version` 被误接到 `Snapshot.version_no`**] → D10 已写明它是 `snapshot_time` 的渲染；`Snapshot` 的 docstring 亦已写明存储层用 `id` 作引用键。`17` §10.7 的示例串与 `version_no` 整数**形态不同**，接错会立刻在测试里显形。
- [`14` §3.4 步 1 曾把「品质库区匹配」列为活判据，而这四个字文档从未定义] → **已按用户决定从全部文档移除**（`14` / `16` 总表与 A.2·A.3 / `17` §3.3 / PRD 两行 / `CONTEXT.md`），逐处改动面见 D7。残留一项：`InventoryItem.zone` **列**的文档来源已全部清退，列本身待独立清退（不由本变更夹带，见 D7）。
- [`permission` 规格的「不存在面向角色的手动触发端点」与本端点并存，字面上有张力] → **已了结**：用户 2026-09-11 决定「订正」，已落 `specs/permission/spec.md` 的 MODIFIED delta（**实质未变** —— 只把口径从端点级绝对收回资源级，与 `13` §2.2 对齐；详见 D10）。**遗留一项时序**：主规格 `openspec/specs/permission/spec.md` 要到归档同步时才换措辞，在那之前它仍是旧的 —— 故本变更归档前，**不得以「主规格已经对了」为前提**去判断任何与 `engine` / `ledger` 手动入口有关的行为。
- [**未导入任何映射 ⇒ 端点在没有种子数据时也应当行为确定**] → 空队列产出空 `plans`；无权重阻断；无 `AisleCap` ⇒ 无可行巷道 ⇒ 每单走「四级走尽 → 失败」。三条路径都有单测。

**性能目标**（引用 `08` §14.1「各模块间的接口契约」的 SLA 数值）：

| 契约（`08` §14.1） | SLA | 在本阶段的落点 |

## Migration Plan

- **无数据迁移**：本变更不新增表、不新增列、不改列类型，迁移链无需 `alembic revision`。空库 `upgrade head` 后 `autogenerate` 应产生**空 diff** —— 这一条作为验收动作保留（`data-model` 变更立下的同一动作）。
- **发布顺序**：先写测试（RED，`tests/logic/test_*.py` 造数）→ 实现 7 个模块（GREEN）→ 接端点（`tests/api/`）→ 逐组件原子提交。单测不允许「先实现后补测试」。
- **回滚策略**：代码回滚 = 分支不合并，或 revert 到 `v0.2.0`；本阶段不写台账、不改既有数据，故**回滚无数据后果**。「功能开关式回滚、不删历史台账」是阶段六 Go/No-Go 的闸门要求，届时实现（D12 已登记接口预留）。
- **与阶段四的接口**：`AisleCap` 的行由阶段四写入、`RecommendationPlan` 的消费方（F5 确认 / F7 落位）也在阶段四。本阶段把契约（`17` §10.1 / §10.7）先定下来，阶段四只接不用改 —— 这正是「**27 必须先于 28**」的含义。
