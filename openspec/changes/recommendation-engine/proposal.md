## Why

当日入库队列的落位目前没有引擎。v0.2.0 已交出 23 个实体与权限矩阵，但 `app/engine/` 的 8 个文件仍只有 docstring 骨架，`POST /api/allocate/batch` 是一条空路由 —— 决定「**谁先挑**稀缺的近站台容量」与「**挑哪个**巷道」的两个动作都还不存在。

这正卡在要治的根因上：**均分即散落**（同物料在库内跨巷道 11.7~22.4，单张 DO 跨 6~8 巷道，出库退化成「全库筛」）。没有优先级排序，爆款与慢流转品会被同等对待；没有预留池，近站台的黄金库容会被 B/C 类先占掉。

本变更落在关键路径 `F1 → F2 → F9 → F3 → F4 → …` 的 **F3**（物料号级评分引擎，含当日队列批量分配 + 近站台预留）与 **F4**（软推荐巷道集，带理由）两环，并遵守「**27 必须先于 28**」—— 引擎产出要被交易侧消费。

## What Changes

- **6 因子评分**：`abc` / `cap` / `existing` / `station` / `batch` / `continuity`（固定集，不得增删），权重取 `WeightConfig` 的当前生效版本；同输入必得同输出
- **当日队列批量竞争分配**：队列构建 → 优先级排序（三项加法：未来 N 天交货单出库量 / ABC 等级 / 既有集中度增益）→ 资源快照（含预留扣减）→ **贪心**分配（`14` §3.4）
- **近站台预留池**：`cap_reserved = cap_total × 40%`，仅近站台巷道；**非 A 类不得占用**；配置时点（默认 18:00）未被 A 类用完即自动释放给 B/C
- **四级降级链**（近站台 → 次近巷道 → 远巷道 → 溢出区）：容量不足时逐级下探，**每步记录降级原因**；A 类爆款被迫降级 → 触发告警（含「近站台缺口 X 板，建议移库腾挪」）
- **推荐理由的可追溯契约**：每巷道 × 每因子的取值与**取值说明**、**两种互不混用的降级标记**（方案级 `degraded` / `degrade_reason` 对应降级链；因子级 `factor_degraded` 对应数据缺失）、预测跨巷道
- **端点 `POST /api/allocate/batch`**：请求**显式**给出参与本次容量竞争的单据集合（不设「空即全量」的隐含默认）；响应按 `priority` 降序，回写 `bulk_batch_no`，`JobOrder` 迁移 `PENDING → PLANNED`
- **本阶段不写台账**：只产出 `RecommendationPlan` 与作业单状态推进；落位执行、后验与台账写入属 F7 / F8（阶段四）

## 非目标

- **不做文件导入管线**（F1 / F2，阶段四）—— 故本阶段**无真实数据**：cap 基线、既有库位分布、ABC 分类、巷道-站台主数据四类输入全为空。这不是缺陷，是 `16` §394 / `A.4` 已写明的预期状态：四类输入各自「**因子降级不参与评分**并在推荐理由中标注降级原因，**不阻断**作业」
- **不做落位执行与台账写入**（F7）、**不做后验**（F8）、**不做 KPI 看板**（F10）—— 本阶段不产生任何 `Ledger` 记录
- **不做出库顺路取**（F10）—— 出库是**只读派生**，不触发评分引擎、不重新决定落位
- **不做移库收拢方案**（M1 路线图）、**不做库位族推荐**（F6，阶段四）
- **不做全局最优**（小规模整数规划 / 局部交换）—— 首期按优先级的贪心分配，全局最优是路线图
- **不做 cap 漂移对账与告警持久化**（F9，阶段四）；本阶段只**读** cap 基线并做事务内扣减
- **不做前端页面与对话台 UI**（阶段七）；本阶段不含任何 `.html` / CSS 令牌改动
- **不接冷路径 LLM** —— 评分与排序本地确定性，`LLM 不参与实时评分与排序` 是红线

## Capabilities

### New Capabilities

- `recommendation-engine`: 6 因子确定性评分、当日队列批量竞争分配（优先级排序 + 近站台预留扣减 + 四级降级链）、推荐理由的可追溯契约（每因子取值/取值说明 + 两种降级标记 + 预测跨巷道）、`POST /api/allocate/batch` 端点

### Modified Capabilities

- `permission`：订正 `自动写权限封闭` 的**表述**（实质未变）。该条现写作「任何角色都不得通过手动入口触发台账写入或引擎调用」，其场景更直言「不存在面向角色的手动触发端点」—— 而本变更要交付的 `POST /api/allocate/batch` 正是一条**持 `inbound.operate` 的角色可调、且会触发引擎**的端点，字面上与之冲突。

  订正方向以事实来源为准：`13` §2.2 的 `engine` 行原文是「`invoke`（系统内部调用，**不向业务角色开放手动触发**）」，§2.2 图例亦称「自动 = 由作业流 / 引擎自动执行，不向角色暴露手动入口」—— 两条讲的都是**资源不得被授予**，不是「系统不存在任何会触发引擎的端点」。故订正为：`ledger.write` / `engine.invoke` 恒不可授予、且不得以 `ledger` / `engine` 为**目标资源**设手动接口；引擎调用只能作为**业务动作的内部后果**发生，授权依据是该业务动作的资源标识（本端点为 `inbound.operate`）。**新增一条场景**固化这个读法。详见 `design.md` D10。

- `data-model`：**不改** —— `JobOrder 状态机` 已含 `PENDING → PLANNED`，实体清单不新增实体。

（`permission` 的 `v1 不做端点级资源鉴权` 保持原样：本端点同样**不挂 403 资源级鉴权**，该条的字面与场景均仍成立。）

## Impact

**代码**

- `backend/app/engine/{factors,priority,scoring,allocator,reserved,degradation,reasons}.py` —— 现为骨架占位，本变更实现
- `backend/app/api/routes/allocate.py`（现为空 `APIRouter`，按 TDD 先写测试再加端点）、`backend/app/schemas/reason.py`（`17` §10 的 JSON 结构）、`backend/app/main.py`（路由注册）

**实体**（无列变更，仅读写口径）

- 写：`RecommendationPlan`（`payload_json` 按 `17` §10.1 扩展）、`JobOrder`（`bulk_batch_no` 回写 + `PENDING → PLANNED`）
- 读：`WeightConfig` / `CapacityConfig` / `AisleCap` / `Aisle` / `AisleStation` / `Material` / `InventoryItem`

**API**

- 新增 `POST /api/allocate/batch`

**权限口径**（与 `permission` 规格的边界）

- 该端点由入库作业的**批量分配动作**触发，目标资源标识为 `inbound.operate`；**引擎调用本身不向任何角色暴露** —— `engine.invoke` 恒不可授予（`engine.invoke` 为自动权限，见 `AUTO_ONLY`）
- 按 `permission` 的 `v1 不做端点级资源鉴权`：本阶段**不挂 403 资源级鉴权**，越权由角色菜单可见性 + 二次确认承担；该端点的 401 由既有认证中间件覆盖
- 该端点与本条口径的**字面张力已订正**（`自动写权限封闭` 的 MODIFIED delta，见 Capabilities）—— 订正只把口径从端点级绝对收回资源级，本端点的行为与 403 / 401 的处置**均不变**
- 本端点**不产生台账**，故不适用「未确认不产生台账」的二次确认要求；二次确认发生在后续的落位确认（F5 / F7，阶段四）

**KPI 与验收**

- 同物料跨巷道 `≤5`：本阶段以 `predicted_cross_aisle` **预演**（分配后预测），非落位后实测
- 同批跨巷道 `≤3`：入库侧**分配时刻不可算**（`14` §3.1 —— PO 不含批号，批号在入库过账时生成），留待后验
- 性能 SLA：单物料评分 `≤1s`；单次批量单据 `≤50` 单
