## Why

阶段二归档后做的两轴代码评审（固定点 `5da396a`、HEAD `194c346`）挑出一条：`auth` 规格的
「凭据无效、缺失、过期或签名错误时，系统必须一律返回 401，且**不得区分失败原因**」与
`app/api/middleware.py` 的实现冲突 —— 中间件把 `SessionInvalid` 的逐因文案
（「会话已过期，请重新登录」vs「会话凭据签名不匹配」vs「缺少必要字段: …」）抄进了 401 响应体。

**查证后认定：该冲突的责任在规格一侧。** 全部 `产品设计/` 文档 grep「不区分」**零命中**；
`13` §6.1 第 3 步只说「凭据无效或缺失则返回 HTTP 401，前端引导至登录页」。真正有来源的
「不区分」只落在**前端登录表单**上（`22` §2.1 / §2.3 固定红字「账号或密码错误」），
而那一半实现已经做到（`routes/auth.py` 的 `LOGIN_FAILED` 对「用户名不存在 / 密码错误 /
账号非激活」一视同仁）。这条规格是**从中间件的类 docstring 反向长出来的**，比事实来源宽。

宽的代价不是安全，而是**诊断力**：`decode_session_token` 的顺序是
「结构 → 算法 → 签名 → 载荷语义」（`security.py:202`，验签在 `:228`，解释载荷在 `:232`），
所以逐因文案分两截 ——

- **未认证就够得着的**（缺凭据 / 段数不对 / 缺签名段 / 头不是 JSON / 算法不受支持 /
  签名不匹配）：描述的全是**客户端自己发过来的东西**，没有一条泄露服务端结构；
  唯一沾边的是「仅 HS256」，而 D7 已写明不做算法协商，HS256 是公开事实。
- **必须已有合法签名才够得着的**（缺字段 / 类型不合法 / 已过期 / 载荷不是 JSON）：
  够得着的人要么是合法签发方 —— 逐因文案是**应该**给他的诊断信息 —— 要么持密钥。

而 `_unauthorized(str(exc))` 是当前**唯一**把失败原因带出中间件的通道（`app/main.py` 有
logger，但认证路径一行都不记）。收紧成统一文案后，线上一个 401 将无法分辨是过期、被吊销
还是载荷被改 —— 而排查「管理员置 `disabled` 之后旧凭据为何仍通行」正需要它。

## What Changes

- 把 `auth` 能力的「登录端点与失败语义」一条 Requirement **收窄到它有事实来源的范围**：
  免费认证与「失败提示一致」的要求保留（且只针对 `/api/auth/login`），
  删去「不得区分失败原因」这句被写成覆盖**全部 401** 的表述；场景**不动** ——
  「失败原因不区分」那个场景本来就是登录表单的，属已达成且有来源的部分。
- 订正 `app/api/middleware.py` 的类 docstring：「**不区分原因（避免成为探测面）**」
  与代码不符，且多半是上面那句规格被写宽的源头。改为写清真正的硬边界 ——
  **不返回 404、不泄露路由是否存在**（`permission` 能力的「访问边界与免认证白名单」
  有明确要求，已实现）。

**本change 不改任何行为，也不改任何代码逻辑 —— 只改一行 docstring 与一份规格。**

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `auth`: 「登录端点与失败语义」一条 Requirement 的**作用域**收窄 ——
  免认证与「登录失败响应体一致」保留并明确限定在 `/api/auth/login`；
  移除对**凭据校验路径**（中间件的 401）「不得区分失败原因」的要求。

`permission` 能力**不改**：它的「访问边界与免认证白名单」只要求 401 而非 404、白名单恰好四条，
与本次收窄无关，且实现已满足。

## 非目标

- **不改 401 的任何行为**：不改状态码、不改响应体形状（`error` / `message` 两键）、
  不改逐因文案的内容与长度。这是**纯规格口径**变更。
- **不引入认证路径的日志**。保留诊断力的更优做法是把原因记进日志，但认证路径的可观测性
  该随阶段三之后统一做，本 change 不为一条 message 单开一个口子（已在本次评审中登记为
  可选后续）。
- **不做端点级资源鉴权（403）**，不碰 `permission` 能力，不触碰「不做清单」任何一项。
  本 change 与 `24` 号红线无关，不涉及核心链路、不涉及 LLM、不涉及数据出域。
- **不新增「401 响应体形状」的场景**（`error` / `message` 两键、`error` 取值
  `unauthenticated`）。它确实是一份已实现的可观测契约（前端拦截器将来按 `error` 分流），
  但那是**新增**要求而非收窄，按 `## MODIFIED` 的规矩不该混进来；且前端要到阶段七才消费它。
  登记在此，需要时单开一项。
- **不补「首个管理员账号无创建路径」等阶段二遗留项**（它们已登记在归档的 `tasks.md`
  9.4g / 9.4l，等待设计负责人裁决），本 change 不顺手处理。

## Impact

- **实体**：无。
- **API 路由**：无。`/api/auth/login` 与认证中间件的对外行为逐字不变。
- **KPI 指标**：无。
- **受影响文件**：`backend/app/api/middleware.py`（仅类 docstring 一行）、
  `openspec/specs/auth/spec.md`（经 `## MODIFIED Requirements` delta 修改）。
- **与关键路径的关系**：不落在 `F1 → F2 → F9 → F3 → …` 的任何一环上。它是 `26` 号
  （数据模型 + 权限）留下的地基口径，阶段二交付时未发现，本次评审后订正。
